option 3 · read path

how moments become context.

writes were the easy half. this is how the moments table becomes a usable prompt and a usable tool surface — and how it plays with the brain loop turn by turn. the unsexy crux. get this wrong and the whole stream is dead weight.

1. the problem

"load today's moments into context" is a one-line idea that doesn't survive contact with token budgets.

back of envelope, for a normal day:

  • ~250 moments in a busy day, average ~80 tokens serialized → ~20k tokens just for today
  • last 7 days → ~140k tokens. that's the whole context window for one bundle, before the user's message, before the conversation, before tools.
  • and 95% of that is noise the model won't use this turn.

so the question isn't "what do we store" — that's already solved. the question is: given a stream of moments, how do you assemble the right ~3k tokens for this turn, and let the model pull more on demand when it isn't enough?

two-mode answer. some context is always needed — a thin curated bundle, computed eagerly per turn. some context is sometimes needed — exposed as tools the model can call. hybrid. anything else is broken at the extremes.

3. lazy tools — the model pulls more on demand

for the ~20% of turns where the bundle isn't enough, the model has tools. it iterates, the loop responds, more moments load only when needed.

toolshapetypical use
get_day(date) all moments for one date, grouped by kind "what happened last tuesday"
query_moments({kind?, range?, entity?, origin?}) flexible filter, paginated "every commitment about marc this month"
get_entity(name_or_id) node + edges + last N moments touching it "refresh me on sarah"
search_text(q, k=10) pgvector search over moments.body "that thing they mentioned about the apartment"
trace(moment_id) follow caused_by chain back to observed roots "why does donna believe X" — provenance
get_narrative(date_range) sealed narratives for a span "what was last month like"
get_rhythms({dow?, confidence_min?}) pattern rows "what's normal for them on fridays"
tool-call cost is real. each tool call = another round-trip through the model. budget 2-3 tool calls average per turn before it starts feeling slow. design tools to return enough that the model doesn't need to iterate ten times.

annotated pseudocode

async function runTurn(user_id, user_input, conversation_id) {
  // 1. write the inbound moment immediately
  const in_moment = await writeMoment({
    user_id, origin: 'observed', actor: 'user',
    kind: 'message', body: user_input
  });

  // 2. assemble eager bundle (parallel queries)
  const bundle = await assembleContext({
    user_id,
    conversation_id,
    mentioned: extractMentions(user_input),
  });

  // 3. build messages array
  const messages = [
    ...conversationHistory(conversation_id, last=20),
    { role: 'user', content: user_input }
  ];
  const system = SYSTEM_PROMPT + '\n\n' + bundle.render();

  // 4. tool loop — exit on terminator or max_iter
  for (let i = 0; i < MAX_ITER; i++) {
    const resp = await anthropic.messages.create({
      system, messages, tools: TOOLS
    });

    for (const block of resp.content) {
      if (block.type === 'tool_use') {
        const result = await TOOLS[block.name](block.input, { user_id });
        // every tool call becomes a moment — donna's actions are traceable
        await writeMoment({
          user_id, origin: 'acted', actor: 'donna',
          kind: 'tool_call',
          payload: { tool: block.name, input: block.input, result_summary: ... }
        });
        messages.push({ role: 'tool', content: result });
      }
      if (block.type === 'tool_use' && TERMINATORS.has(block.name)) {
        // send_burst — write outbound moments and exit
        for (const burst of block.input.bursts) {
          await writeMoment({
            user_id, origin: 'acted', actor: 'donna',
            kind: 'donna_message', body: burst,
            caused_by: in_moment.id,
          });
          await sendToUser(burst);
        }
        return;
      }
    }
  }

  // 5. async — extractor processes new moments → emits inferred moments
  enqueueExtraction(in_moment.id);
}

5. assemble_context — the function that matters

this is the engineering centerpiece. seven small functions, parallel, each producing a slice of the bundle.

todaycompressed
raw query: SELECT kind, payload, ts FROM moments WHERE user_id=$1 AND date=today ORDER BY ts. then a per-kind renderer collapses to one-liners. counts where it makes sense, key fields where it matters. 
render(moments) ⟶
"today so far (2026-05-21, tue):
  meetings: standup 10:00 ✓, marc 1:1 14:00 ✓
  commitments open: book dentist (due 17:00), call mom
  donna sent: 1 morning brief, 1 nudge re dentist 17:00
  mood signal: replies slower than usual"
recent narrativeslast 7 days
cheap join. one row per day. summary field only. 
SELECT date, summary, energy
FROM day_narrative
WHERE user_id=$1 AND sealed=true
  AND date BETWEEN today-7 AND today-1
ORDER BY date DESC;
active threadsnot yet closed
moments of kind=commitment where no superseding resolution exists, within a recency window so it doesn't grow forever. 
SELECT m.* FROM moments m
LEFT JOIN moments r
  ON r.supersedes = m.id
  AND r.kind = 'commitment_resolved'
WHERE m.user_id=$1
  AND m.kind='commitment'
  AND m.ts > now() - interval '14 days'
  AND r.id IS NULL;
entity hot-cacheconversational
maintained per-conversation in redis (or in-memory). every turn extracts mentioned entity ids, unions with rolling window, evicts oldest. when assembling, fetch node + 1-hop edges for each.
conversation windowraw
last N message-kind moments for this conversation_id. cheap. raw text. the model needs actual phrasing here, not compressed.
rhythm hintday-of-week
SELECT kind, signature, typical_time, confidence
FROM rhythms
WHERE user_id=$1
  AND dow = extract(dow from today)
  AND confidence > 0.5
ORDER BY confidence DESC
LIMIT 6;
identity ribboncached
one query at sign-in, refreshed daily. user node + top edges by recency × confidence. cached in memory per process.

8. failure modes

failuresymptomfix
bundle too thin model tool-calls every turn, latency creeps up, cost rises measure tool-call rate; promote frequently-pulled data into the bundle
bundle too fat cost balloons, signal-to-noise drops, model starts ignoring the bundle shrink each component; rotate stale narratives out; compress more
stale entity cache model talks about sarah using week-old facts invalidate entity cache when graph edges change
rhythm hint misleads "unusual for tuesday" fires on weeks when life isn't on rails cap rhythm assertions in voice; only act on multi-week patterns
extraction lag this turn's moments aren't extracted yet → bundle missing fresh inferences fine — inferences land in next turn's bundle. extractor is async by design
moments table grows fast queries slow as table hits hundreds of millions of rows partition by (user_id, month); archive cold partitions to s3 after 1y

9. the through-line

writes are easy. reads are where the architecture either earns its keep or doesn't.

moments-stream gives you one table to write to and one table to query from. but the model can't query a million rows — so the engineering job is context assembly: a small, fast, parallel set of queries that produce ~3k tokens of curated signal every turn, plus tools that let the model fetch more when the bundle isn't enough.

the brain loop barely changes. it gets a fatter system prompt (the bundle) and a richer tool set. every action it takes writes back into moments, so donna's own behavior becomes future context. closed loop.

the underrated property: because donna's actions are moments too, she can reason about herself. "did i nudge them about this already" is a query, not a guess. that's the difference between a stateful assistant and one who forgets she just texted you.
