option 2 of 3

event-first. everything else is a projection.

only one table holds truth — events. day_entries, narratives, graph, rhythms are all marked derived: drop and rebuild any of them from the event log without losing a thing. extraction is a pure function. replay is a first-class operation, not a recovery story.

1. thesis

donna's understanding is a function of what she's seen. capture what she's seen with absolute fidelity in one append-only log. compute everything else. the discipline isn't storage — it's making sure no derived table ever holds information that can't be reproduced from the log.

the strong claim: if you can't drop the graph table and rebuild it from events overnight and get the same answers, you've leaked state outside the log. that's a bug, not an optimization.

events — the single truth table

{
  id           uuid pk,
  user_id      uuid not null,
  ts           timestamptz not null,        -- when it happened
  ingested_at  timestamptz not null,        -- when donna saw it
  source       source_enum not null,        -- whatsapp, imessage, gmail, cal, donna, system
  actor        actor_enum not null,         -- user, donna, system, external
  kind         event_kind not null,
  payload      jsonb not null,
  supersedes   uuid references events(id),  -- for corrections
  created_at   timestamptz default now()
}

-- partitioned by (user_id, month) for replay-by-user efficiency
-- indexes: (user_id, ts), (user_id, kind, ts), (supersedes)

event kinds

  • message_in / message_out — chat with donna
  • integration_delta — gmail thread, calendar change, etc
  • donna_action — notification fired, reminder sent, tool called
  • fact_asserted — user told donna something declarative
  • fact_corrected — supersedes a prior fact
  • observation — donna noticed something (separate event so extraction is auditable)

derived tables

same shapes as option 1 for d_day_entries, d_day_narrative, d_entities, d_edges, d_rhythms. the difference is enforcement: writes only via the extractor pipeline, and the pipeline is a pure function over events.

3. write path — and replay path

flowchart TB
  IN[message / integration / donna action] --> EV[(events)]
  EV --> Q[event queue]
  Q --> EX[extractor v_N]
  EX --> RUN[(extraction_runs)]
  EX --> DE[(d_day_entries)]
  EX --> DG[(d_entities + d_edges)]
  EX --> DN[(d_day_narrative)]
  CRON[nightly] --> SEAL[seal narrative]
  CRON --> RH[(d_rhythms)]

  REPLAY[replay job
extractor v_N+1] -.->|wipe + rebuild| DE
  REPLAY -.->|wipe + rebuild| DG
  REPLAY -.->|regenerate| DN

live writes

  1. anything observable → event written first. nothing else.
  2. extractor consumes events from a queue. produces derived rows. records its version in extraction_runs.
  3. downstream tables update as a consequence — never directly.

replay

when extractor logic improves, replay runs against historical events. derived tables wipe and rebuild. yesterday's data gets smarter without re-collecting. this is routine, not exceptional.

extraction must be pure. input: (event, current derived state). output: (derived rows to write). no calls to external apis during extraction. no random ids generated. no time.now(). everything reproducible.

4. read path

identical to option 1 from the model's perspective — same tools, same bundle. the model has no idea anything is derived. that's the point.

5. worked example — the 5pm dentist nudge, with a twist

same scenario as option 1, but two weeks later the extractor learns to detect dental anxiety from earlier messages. replay runs. yesterday's data is now smarter.

sequenceDiagram
  participant U as user
  participant D as donna
  participant E as events
  participant EX as extractor v1
  participant DT as derived

  U->>D: "remind me to book the dentist tomorrow"
  D->>E: event(kind=message_in)
  E->>EX: process
  EX->>DT: d_day_entries(commitment, dentist, due=tomorrow 5pm)
  EX->>DT: d_edges(user, has_appointment_with, dentist)

  Note over E,DT: extractor v2 ships — detects dental anxiety
  D->>EX: replay last 90 days with v2
  EX->>DT: WIPE + REBUILD d_day_entries, d_edges
  EX->>DT: now also: observation(user_has_dental_anxiety, evidence=...)

  Note over D: today 5pm — donna nudges with softer language
  D->>U: "ready to make the dentist call? no rush."

donna's nudge gets softer not because someone updated a row — because replay surfaced a pattern the old extractor missed. no new data was collected. the user's history just got smarter.

6. rhythms — same idea, different discipline

same shape as option 1. the difference: d_rhythms is computed only from events + d_day_entries. if rhythm logic improves, drop and recompute. patterns aren't sacred — they're a current best-guess from current understanding.

7. tradeoffs

good at

  • upgradability — past data gets smarter on every release
  • provenance — every derived row links to events
  • recovery — table corruption is a non-event, replay it
  • schema courage — change derived shapes freely
  • debuggability — "why did donna think X" → trace

costs

  • worker / queue infrastructure required from day one
  • eventual consistency — derived tables lag behind events
  • extraction discipline (purity) takes engineering taste
  • more moving parts in v0
  • "why is today's snapshot empty?" → did the extractor run?

8. when to pick this

pick this if you expect donna's understanding to evolve fast and you want every past day to come along for the ride. it is the choice that pays compound interest over years — but front-loads infrastructure work.

opt 1 trades this for ergonomics. opt 3 trades it for mental simplicity.
