# Donna v0.2 — Proactive Brain

**Date:** 2026-05-08
**Status:** Brainstorming
**Builds on:** v0.1 (reactive brain, supabase persistence, send_burst terminator, gmail/composio integration)

## Purpose

Make Donna proactive without building a parallel system. The same `runTurn` loop that handles reactive WhatsApp turns also handles every proactive wake-up. Mode-switched at the entry point: different system prompt, gated tool subset, extended terminator family. Everything else — voice filter, caching, message persistence, observability — is identical.

The bet: proactivity is **not** a separate brain, a notification engine, or a templated alert pipeline. It is the reactive brain re-entered with a different trigger and a slightly different toolbox. One brain, two modes.

## Non-goals (each is its own future spec)

- Living profile / observations substrate (referenced but not read in v0.2)
- Trust-tier daily quotas, signal-scoring, exploration budget
- Crisis-register suppression, engagement-window adaptation
- Real-time webhook push (Gmail watch API, calendar push channels) — v0.2 polls only
- A separate proactive judge model (Haiku ping/hold/drop) — collapsed into the brain itself
- `list_open_loops`, `list_recent_observations`, `list_calendar_events` tools — referenced for later but not required for the v0.2 spine
- Multi-user trust models — same single-user shape as v0.1

## Core principles

1. **One log.** Both modes write `role: "assistant"` turns to `chat_messages`. Proactive sends are Donna's own messages. Reactive Donna on next inbound sees her own proactive sends as her own history — first-person continuity, no "system sent on her behalf" indirection.

2. **A real brain, not notify-then-template.** Proactive is a full Sonnet tool loop. Same `runTurn`, same `MessageParam[]`, same voice filter on egress, same prompt cache pipeline. The only knobs that change between modes are: (a) system prompt, (b) which tools are visible, (c) which terminators are legal.

3. **Cause-as-synthetic-user-message.** Every proactive wake-up arrives as a tagged user-role message in `chat_messages`:

   ```xml
   <proactive_cause kind="scheduled" set_at="2026-05-04T18:00:00Z">
     remind nikhil about workout, he flagged he's been slipping
   </proactive_cause>
   ```

   This makes the cause part of the unified log — reactive Donna can see *why* she pinged, not just *what* she said.

4. **Everything is a scheduled brain run with a cause.** No separate scheduler / watcher / event-listener subsystems. One table (`donnaschedule`), one cron executor, one entrypoint. Triggers differ only by `cause_kind`. What makes a cause "event-like" is which tools the brain reaches for to evaluate it.

5. **Read-heavy, write-on-consent.** Proactive can read anything and write to Donna's own substrate (schedules, observations, watches). It cannot perform user-visible side-effects beyond `send_burst`. External writes (Notion mutate, send-email-as-user, calendar-mutate) are reactive-only when they exist.

## Brain entrypoint changes

Today `runTurn` accepts `mode: "reactive" | "proactive" | "proactive_tier3"` and throws on anything but `reactive`. v0.2 wires up `proactive`.

### `RunTurnArgs` extension

```ts
export type BrainMode = "reactive" | "proactive";

export interface ProactiveCause {
  kind: "scheduled" | "scan_gmail" | "watch_fired";
  payload: Record<string, unknown>;
  set_at: string;            // ISO timestamp when the cause was authored
  schedule_id: string;       // FK into donnaschedule
}

export interface RunTurnArgs {
  mode: BrainMode;
  messages: MessageParam[];
  userInput?: string;          // required when mode === "reactive"
  cause?: ProactiveCause;      // required when mode === "proactive"
  runId?: string | null;
  langsmithExtra?: { tags?: string[]; metadata?: Record<string, unknown> };
}
```

Validation: exactly one of `userInput` / `cause` must be set. Throw early on misuse.

### Cause → synthetic user message

When `mode === "proactive"`, `runTurn` synthesizes a user-role message at the start of the turn:

```ts
const causeXml = renderCauseXml(cause);  // <proactive_cause kind="..." set_at="...">payload</proactive_cause>
working.push({ role: "user", content: causeXml });
```

That message is persisted to `chat_messages` exactly like a real inbound. Subsequent reactive turns will load it as part of history.

### Per-mode system prompt

Two constants in `src/donna/prompt.ts`:

- `REACTIVE_SYSTEM_PROMPT` — current `SYSTEM_PROMPT`, unchanged.
- `PROACTIVE_SYSTEM_PROMPT` — same voice, `<why_you_exist>`, `<voice>`, `<whatsapp_rules>` blocks. Adds `<proactive_rules>`:
  - "you woke up because of a `<proactive_cause>` block, not because the user spoke."
  - "use tools to gather context before deciding."
  - "your terminators are `send_burst`, `do_nothing`, `defer`. choose silence often."
  - "if the cause is stale (user already addressed this in chat history), prefer `do_nothing`."
  - "match register to the cause kind: scheduled reminders are direct, gmail triage is curated, watches are the read."

Both prompts get `cache_control: ephemeral`. Cache hit rates split between modes — that's fine, they'd diverge anyway.

### Tool gating

Extend each tool definition with a `modes` set:

```ts
type ToolWithModes = ToolWithCache & {
  modes: ReadonlySet<BrainMode>;
};
```

Stored alongside the existing `ToolWithCache` in `tool_definitions`. At the top of `runTurn`, filter:

```ts
const allowedTools = tool_definitions.filter(t => t.modes.has(mode));
```

The model never sees tools it can't call in the current mode. Cleaner than reject-after-call — saves a wasted iteration.

For server tools (`code_execution`), `modes` defaults to both. Same for `send_burst`.

### Terminator extension

`TERMINATORS` becomes mode-aware:

```ts
const TERMINATORS_REACTIVE = new Set<string>(["send_burst"]);
const TERMINATORS_PROACTIVE = new Set<string>(["send_burst", "do_nothing", "defer"]);
```

Loop logic unchanged: any terminator hit ends the iteration. The `RunTurnResult.terminator` type widens to `"send_burst" | "do_nothing" | "defer" | "cap_hit"`.

### Result shape

`RunTurnResult` gains:

```ts
nextSchedule?: {
  fire_at: string;     // ISO
  cause: ProactiveCause;
};
```

Populated when the brain calls `defer`. The caller (executor cron) is responsible for inserting the new `donnaschedule` row.

### New tool: `do_nothing`

```ts
input_schema: {
  type: "object",
  properties: {
    reason: { type: "string", description: "why this cause did not earn an interrupt" }
  },
  required: ["reason"]
}
```

Handler: log `reason` to execution_observability, return `"acknowledged"`. The brain's assistant turn (containing this tool call + voice filter pass) still persists to `chat_messages` — no user-visible message, but Donna's reasoning is preserved.

### New tool: `defer`

```ts
input_schema: {
  type: "object",
  properties: {
    fire_at: { type: "string", description: "ISO timestamp when to wake again" },
    cause: {
      type: "object",
      properties: {
        kind: { type: "string", enum: ["scheduled", "scan_gmail", "watch_fired"] },
        payload: { type: "object" },
        instruction: { type: "string", description: "what donna should remember to do on next wake" }
      },
      required: ["kind", "instruction"]
    }
  },
  required: ["fire_at", "cause"]
}
```

Handler: validates `fire_at` is in the future, returns the new cause spec. The executor inserts the `donnaschedule` row using `RunTurnResult.nextSchedule`. (Tool handler does **not** write to the DB itself — keeps the side-effect under the executor's transaction, atomically with marking the current row `fired`.)

Asymmetry with `create_schedule` is deliberate: `defer` is a terminator wrapping a complete turn, so its DB effect must commit alongside the turn's status transition. `create_schedule` is a mid-turn tool call that creates an *unrelated* future schedule, so it writes immediately.

### New tool: `create_schedule`

For user-set reminders. Reactive use ("remind me at 6pm to call mom") and proactive self-scheduling beyond simple `defer` (e.g., scheduling a recurring weekly check).

```ts
input_schema: {
  type: "object",
  properties: {
    fire_at: { type: "string" },
    instruction: { type: "string" },
    cause_kind: { type: "string", enum: ["scheduled", "scan_gmail", "watch_fired"], default: "scheduled" }
  },
  required: ["fire_at", "instruction"]
}
```

Handler: inserts a `donnaschedule` row directly with `created_by` set per the calling mode (`donna_reactive` or `donna_proactive`). Returns `{ schedule_id, fire_at }`.

`instruction` is authoritative on the `donnaschedule` row. The synthetic `<proactive_cause>` user-message is rendered from the row at executor time, not stored separately. `cause.payload` may carry additional structured data (e.g., gmail query window for `scan_gmail`) but never duplicates `instruction`.

## Substrate

### Migration: `donnaschedule`

```sql
create table donnaschedule (
  id              uuid primary key default gen_random_uuid(),
  user_id         uuid not null references users(id) on delete cascade,
  fire_at         timestamptz not null,
  cause_kind      text not null check (cause_kind in ('scheduled', 'scan_gmail', 'watch_fired')),
  cause_payload   jsonb not null default '{}'::jsonb,
  instruction     text,
  status          text not null default 'pending'
                    check (status in ('pending', 'claimed', 'fired', 'errored', 'cancelled')),
  created_at      timestamptz not null default now(),
  claimed_at      timestamptz,
  fired_at        timestamptz,
  errored_at      timestamptz,
  error_message   text,
  created_by      text not null
                    check (created_by in ('user', 'donna_reactive', 'donna_proactive', 'system'))
);

create index donnaschedule_pending_fire_at on donnaschedule (fire_at)
  where status = 'pending';
create index donnaschedule_user_id on donnaschedule (user_id);
```

`status='claimed'` is held during the turn so concurrent executors don't double-fire. Atomic claim via `update ... where status='pending' and id = ... returning *`.

### Executor module: `src/donna/proactive/executor.ts`

Pure module. No HTTP, no entry point. Exports:

```ts
export async function runScheduleTickOnce(): Promise<void>;
export function startScheduleTicker(intervalMs?: number): NodeJS.Timeout;
```

`runScheduleTickOnce` (single-tick logic):

1. **Sweep stuck-claimed rows.** `update donnaschedule set status='pending', claimed_at=null where status='claimed' and claimed_at < now() - interval '5 minutes'`. Recovers rows from a process that crashed mid-fire.
2. **Atomic claim of next due row:**
   ```sql
   update donnaschedule set status='claimed', claimed_at=now()
   where id = (
     select id from donnaschedule
     where status='pending' and fire_at <= now()
     order by fire_at limit 1
     for update skip locked
   )
   returning *
   ```
   Returns `null` if nothing due. `for update skip locked` makes this safe across N concurrent worker instances.
3. **Pass through arbiter.** If rejected → `status='cancelled'` with reason logged. If arbiter returned `reschedule_at`, insert a new pending row at that time with the same cause.
4. **Load last 50 `chat_messages`** for `user_id`.
5. **Call `runTurn({ mode: "proactive", cause, messages })`.**
6. **Persist new messages** via existing `saveMessages` (the synthetic cause user-msg + the assistant turn).
7. **Handle terminator:**
   - `send_burst` → dispatch via `WhatsAppChannel` / `IMessageChannel` (same delivery path as reactive).
   - `defer` → insert new `donnaschedule` row from `result.nextSchedule` in the same transaction as the status update.
   - `do_nothing` → no delivery, no new schedule.
   - `cap_hit` → log + treat as errored.
8. **Mark current row** `status='fired', fired_at=now()`.

On any exception inside the turn: `status='errored'`, `error_message=...`. No automatic retry in v0.2.

`startScheduleTicker(intervalMs = 30_000)`:
- `setInterval` wrapper around `runScheduleTickOnce`.
- In-process concurrency guard (a `_ticking` boolean) so two ticks never overlap within a single instance.
- Returns the interval handle so the caller can `clearInterval` on shutdown.

### Deployment: separate worker service

Two entry points sharing the same repo and image:

```
src/server.ts             — web entry. webhook ingress only. never imports executor.
src/proactive-worker.ts   — worker entry. starts the ticker. never receives webhooks.
src/donna/proactive/executor.ts — pure module. imported by the worker.
```

`src/proactive-worker.ts` (sketch):

```ts
import "dotenv/config";
import { closeDb, getSql } from "./donna/db.js";
import { startScheduleTicker } from "./donna/proactive/executor.js";

async function main(): Promise<void> {
  if (!process.env.ANTHROPIC_API_KEY) {
    console.error("error: ANTHROPIC_API_KEY not set");
    process.exit(1);
  }
  try {
    await getSql()`select 1`;
  } catch (err) {
    const msg = err instanceof Error ? err.message : String(err);
    console.error(`worker can't reach memory: ${msg}`);
    await closeDb();
    process.exit(1);
  }
  const handle = startScheduleTicker(30_000);
  console.log("donna proactive worker ticking @ 30s");

  const shutdown = async (signal: string): Promise<void> => {
    console.log(`\n${signal} — shutting down`);
    clearInterval(handle);
    await closeDb();
    process.exit(0);
  };
  process.on("SIGINT", () => void shutdown("SIGINT"));
  process.on("SIGTERM", () => void shutdown("SIGTERM"));
}

main().catch(async (err) => {
  console.error("fatal:", err);
  await closeDb();
  process.exit(1);
});
```

`package.json` scripts:

```json
"worker":      "tsx watch --clear-screen=false src/proactive-worker.ts",
"worker:once": "tsx src/proactive-worker.ts",
"start:worker": "node dist/proactive-worker.js"
```

Railway deploys two services from the same repo:
- `donna-web` → `npm start` (existing) → handles inbound webhooks only.
- `donna-worker` → `npm run start:worker` → handles scheduled fires only.

Both services connect to the same Supabase. Atomic claim via `for update skip locked` makes the design safe for any number of worker instances; v0.2 ships with one.

Tick cadence: 30 seconds. Cheap because nothing fires unless `fire_at <= now()`.

### Why two services, not one

- **Isolation.** A hung proactive turn (slow `web_search`, model rate-limit) cannot delay webhook acks.
- **Independent scale.** Webhook traffic and proactive load scale on different curves.
- **Independent crash.** Webhook OOM doesn't kill scheduled fires; worker crash doesn't drop user inbounds.
- **Honest separation.** Webhook = react to user. Worker = act on time. Different jobs, different lifecycles.
- **No "v0.3 will refactor this" debt.** Executor module is reusable from day one.

## Arbiter (thin v0.2)

Module: `src/donna/proactive/arbiter.ts`. Pure function, no DB writes.

```ts
type ArbiterDecision =
  | { allow: true }
  | { allow: false; reason: string; reschedule_at?: string };

function arbitrate(args: {
  user_id: string;
  cause: ProactiveCause;
  recent_messages: MessageParam[];
  now: Date;
  user_tz: string;
}): ArbiterDecision;
```

v0.2 enforces only:

1. **Quiet hours** (default 23:00–07:00 user-local, configurable per user later). Reject with `reschedule_at` set to next 07:00 in user TZ. Hazard-class causes (none in v0.2) would bypass.
2. **Cooldown.** If the most recent assistant message in `recent_messages` is `< 30 min` old (configurable), reject with `reschedule_at = last_send + 30min`. Prevents stacking sends.

Rejected schedules don't fire the brain. Executor either re-inserts at `reschedule_at` (status='pending', new row) or cancels with logged reason.

Deferred to v0.3+: trust-tier quotas, crisis-register suppression, active-chat-with-someone-else suppression, signal-scoring weights.

## Three working causes in v0.2

### `scheduled`

User-set reminder. Created via `create_schedule` tool from a reactive turn ("remind me at 6pm to call mom") or seeded externally for testing.

Brain on wake: reads cause `instruction`, optionally calls `gmail_search` / chat history to check if user already addressed it, then `send_burst` or `do_nothing`.

### `scan_gmail`

Recurring inbox triage. Seeded once per user with a recurring shape (the brain itself re-arms via `defer` after each fire).

Cause payload includes `since` window (e.g., "last 4h"). Brain on wake: `gmail_list_recent` / `gmail_search` for unread or important senders, decides whether anything earns an interrupt. Defers to next 4h slot if nothing.

This is the surface that proves "she just knows" without webhook plumbing — pure poll + brain judgment.

### `watch_fired`

Generic watch. Created via `defer` from a prior turn (or future `create_watch` tool). Cause payload describes what to evaluate. Brain on wake: calls whatever tool is relevant (gmail, web_search later) to check the condition, sends if tripped, defers if not.

In v0.2, watches are bootstrapped manually via `create_schedule` — `create_watch` as a first-class tool waits for v0.3.

## Persistence shape

For a proactive turn, the new messages appended to `chat_messages` are:

1. Synthetic user message:
   ```json
   {
     "role": "user",
     "content": "<proactive_cause kind=\"scheduled\" set_at=\"...\">remind nikhil about workout</proactive_cause>",
     "metadata": { "synthetic": true, "cause_kind": "scheduled", "schedule_id": "..." }
   }
   ```
2. Assistant turn (full content blocks: tool_uses, tool_results, terminator). Same shape as reactive.

`chat_messages` schema needs a `metadata jsonb` column (currently doesn't have one — confirm in plan; if missing, add as part of this migration). Loader (`src/donna/memory/chat.ts`) does **not** filter synthetic messages out — they belong in history because they *are* Donna's thinking trigger.

## Open questions for the plan

1. Cooldown computed from `chat_messages` (last assistant turn) or from `donnaschedule` (last fired row)? Lean: from `chat_messages`, because reactive sends should also gate proactive cooldown.
2. WhatsApp delivery from a proactive turn — does it quote-reply anything? Lean: no, proactive sends are unprompted.
3. `userInput` vs `cause` validation — throw at `runTurn` entry, or earlier at the executor? Lean: both — defense in depth, the entry check is load-bearing.
4. Voice filter on `do_nothing` / `defer` turns — apply or skip? Lean: skip (no user-facing text to filter), but still persist the assistant turn for the log.
5. iMessage delivery for proactive — same channel, quote-reply behavior matches WhatsApp choice. No new infra.

## Test plan

- Unit: tool gating filters correctly per mode; cause→xml renderer; arbiter rejects in quiet hours and cooldown windows.
- Integration: seed a `donnaschedule` row with `cause_kind='scheduled'`, run executor once, assert chat_messages has cause + assistant + send_burst, assert WhatsApp delivery called.
- Integration: seed a `scan_gmail` cause with no interesting unread → assert brain calls `do_nothing` or `defer`, no WhatsApp delivery.
- Integration: seed a `defer` flow — brain defers once, executor inserts new row, second tick fires and brain sends.
- Voice filter check: assert proactive sends pass through `filterSends` exactly like reactive.
- Caching: assert system prompt + tools cache_read on second proactive turn within 5min.
