# Donna v0.1 — Supabase Persistence + Burst & Skip Terminators

**Date:** 2026-05-05 (revised 2026-05-06)
**Status:** Approved (brainstorming)
**Builds on:** v0 (`v0.0.1` tag, commit `c581af7`)

## Purpose

Two changes that ship together:

1. **Persistence.** Stop losing Donna's memory between process restarts. Persist every chat message — both directions, every turn — to Supabase Postgres. On each new turn, seed the BRAIN loop with the last N messages from the database.
2. **Response model.** Replace "raw assistant text is the reply" with the terminator-tool pattern from CLAUDE.md: Donna only talks via `send_burst` (one or many messages), or chooses silence via `skip`. Plain text in the model's response is internal reasoning that never reaches the user.

Bundling them is intentional: storage shape and response shape are mutually load-bearing. Doing them in one ship means the chat_messages format settles correctly from line 1 — no retrofit when bursts arrive.

The CLI is the test surface. The same persistence + burst layer will sit behind WhatsApp ingress later.

## Non-goals

Each is its own future spec.

- Async subagents and the `subagent_runs` table
- Parallel tool execution (single-file refactor in `brain.ts`, separate spec)
- Other memory backends (Graphiti, observations, open loops, user-facts, calendar, etc.)
- Context builder blocks (USER MODEL, SITUATION BRIEF, TODAY, etc.)
- Multi-user, Supabase Auth, RLS
- WhatsApp ingress / egress
- Hooks (PreToolUse / PostToolUse)
- Proactive mode (Tier 2 / Tier 3) — schema admits `mode='proactive'` but no v0.1 code writes it
- Streaming output
- A separate "conversations" or "sessions" table — there is exactly one ongoing thread per `user_id`
- Inter-burst delays / typing indicators (CLI prints sends back-to-back; WhatsApp later may add timing)

## Response model — burst & skip terminators

Today (v0): the model returns text, the CLI prints it. The "reply" is the trailing text block of the final response.

v0.1: the model **must** end every reactive turn by calling exactly one of two terminator tools.

### `send_burst({ messages: string[] })`

The model passes one or more strings. The handler emits each as its own visible send — separate console lines today, separate WhatsApp messages eventually. The handler's `tool_result` content is `"sent N message(s)."`. Each terminator tool call ends the BRAIN loop after the tool_results are recorded, even if the response could keep going.

Single-message reply: `send_burst({ messages: ["7:48 pm in tokyo. tuesday."] })`. Burst: `send_burst({ messages: ["going for a run, nice", "btw your form's been off since tuesday", "think about it"] })`.

### `skip({ reason?: string })`

The model decided not to reply this turn. Useful when proactive turns evaluate and back off, or when a user message doesn't actually call for a response. The handler's `tool_result` is `"ok, staying silent."`. The CLI prints nothing visible to the user (a debug indicator may appear in stderr).

`skip` produces zero visible sends but **does** persist the same way every other turn does — the user message + the tool_use(skip) + the tool_result row are stored. That's how we know later "she chose silence here."

### Why terminators rather than free-form text

- **Raw text leaks.** Without this rule, a 3-paragraph reply tempts the model to dump reasoning into the visible reply. With send_burst, every visible send is an explicit, intentional act.
- **Skip is real.** Proactive Donna will sometimes evaluate "should I reach out?" and answer no. Without `skip`, the model has no way to express that — it'll always produce text, and we'll have to filter it heuristically.
- **One handler, one place to control delivery.** Future inter-message delays, typing indicators, surface_at quadrants (CLAUDE.md mentions push/persistent matrices for proactive Tier 3) all live inside `send_burst` — no scatter.
- **It matches CLAUDE.md.** "Only true terminator is `send_burst`." This is the seed of that.

### How the BRAIN knows the turn is over

`brain.ts` keeps a hardcoded `TERMINATORS = new Set(["send_burst", "skip"])`. After running tool handlers in a loop iteration, if any of the executed tool_uses had a name in `TERMINATORS`, the loop exits — even though the model would technically be allowed to call more tools. The accumulated tool_results still get pushed to `working` (and persisted) so the next turn loads a valid `messages[]` array.

If the loop hits `MAX_LOOP_ITERATIONS = 10` without a terminator, the existing fallback message kicks in: `"sorry, got stuck in a loop. try again."` — printed as a single send. (We may upgrade this to actually call send_burst with the fallback in v0.2.)

## Schema

One table for v0.1.

The migration file lives at `supabase/migrations/<timestamp>_chat_messages.sql` (created by the Supabase CLI; see Migration tooling below). Its body:

```sql
create table chat_messages (
  id          uuid          primary key default gen_random_uuid(),
  seq         bigserial     not null,
  user_id     uuid          not null,
  role        text          not null check (role in ('user', 'assistant')),
  content     jsonb         not null,
  mode        text          not null check (mode in ('reactive', 'proactive')),
  created_at  timestamptz   not null default now()
);

create index idx_chat_messages_user_seq
  on chat_messages (user_id, seq desc);
```

Field notes:

- **`id`** — uuid primary key. `gen_random_uuid()` is built into Postgres 13+; Supabase runs 15+, no extension needed.
- **`seq`** — `bigserial`, monotonically increasing per insert. The actual order key. We sort by `seq desc` for "most recent first," not by `created_at`, because `created_at` can tie inside a single turn's batch insert.
- **`user_id`** — uuid. Provided via `DONNA_USER_ID` env var today. Will be derived from phone number when WhatsApp lands.
- **`role`** — `'user'` or `'assistant'`. Matches Anthropic API roles. **No alternation constraint at the storage layer** — see "Loader normalization" below.
- **`content`** — `jsonb`. The full Anthropic content array (`ContentBlock[]`), serialized verbatim. We **always normalize to array form** before storing — even a plain user string `"hi"` is stored as `[{"type":"text","text":"hi"}]`.
- **`mode`** — `'reactive'` for v0.1. `'proactive'` admitted but unused.
- **`created_at`** — wall-clock for human-readable ordering and audit.

The compound index `(user_id, seq desc)` powers the load query. Multi-user readiness from day one.

### What a turn looks like in storage

A reactive `send_burst` turn with one message ("hi" → "hi back."):

```
seq | role      | content                                                                  | mode
----+-----------+--------------------------------------------------------------------------+----------
  1 | user      | [{type:"text", text:"hi"}]                                               | reactive
  2 | assistant | [{type:"tool_use", id:"toolu_…", name:"send_burst",                      | reactive
    |           |   input:{messages:["hi back."]}}]                                        |
  3 | user      | [{type:"tool_result", tool_use_id:"toolu_…", content:"sent 1 message."}] | reactive
```

A reactive turn that uses `get_current_time` then bursts:

```
seq | role      | content                                                                                  | mode
----+-----------+------------------------------------------------------------------------------------------+----------
  4 | user      | [{type:"text", text:"what time is it in tokyo?"}]                                        | reactive
  5 | assistant | [{type:"tool_use", id:"toolu_a…", name:"get_current_time",                               | reactive
    |           |   input:{timezone:"Asia/Tokyo"}}]                                                        |
  6 | user      | [{type:"tool_result", tool_use_id:"toolu_a…",                                            | reactive
    |           |   content:"2026-05-06T14:08:42 (Asia/Tokyo)"}]                                           |
  7 | assistant | [{type:"tool_use", id:"toolu_b…", name:"send_burst",                                     | reactive
    |           |   input:{messages:["2:08 pm in tokyo. wednesday."]}}]                                    |
  8 | user      | [{type:"tool_result", tool_use_id:"toolu_b…", content:"sent 1 message."}]                | reactive
```

Skip turn:

```
seq | role      | content                                                                  | mode
----+-----------+--------------------------------------------------------------------------+----------
  9 | user      | [{type:"text", text:"k"}]                                                | reactive
 10 | assistant | [{type:"tool_use", id:"toolu_…", name:"skip", input:{}}]                 | reactive
 11 | user      | [{type:"tool_result", tool_use_id:"toolu_…", content:"ok, staying silent."}] | reactive
```

Notice: chat_messages stores the BRAIN's view, including tool plumbing. To reconstruct "what the user actually saw," parse `tool_use(send_burst)` rows for their `input.messages` array. We don't double-store the visible-send strings as their own rows — the tool_use row already has them.

### `src/donna/db.ts` (~25 lines)

- Exports `closeDb()` for clean shutdown

### `src/donna/memory/chat.ts` (~80 lines)

- `loadRecentMessages(userId, limit = 50): Promise<MessageParam[]>`
  - Queries `select role, content from chat_messages where user_id = $1 order by seq desc limit $2`
  - Reverses to chronological order
  - Runs the `coalesce` step before returning
- `saveMessages(userId, messages, mode): Promise<void>`
  - Inserts one row per message
  - Normalizes string content to `[{type:"text", text:...}]`
  - Does NOT coalesce — preserves one row per logical message moment
- Internal `coalesce(rows): MessageParam[]` — merges consecutive same-role rows into single API messages

### Loader normalization (coalesce)

Storage allows non-alternating rows (bursts, proactive sends, hook-emitted messages). The Anthropic API does not — `messages[]` must alternate user / assistant. So `loadRecentMessages` coalesces:

```ts
function coalesce(rows: ChatRow[]): MessageParam[] {
  const out: MessageParam[] = [];
  for (const row of rows) {
    const last = out[out.length - 1];
    if (last && last.role === row.role) {
      const prev = Array.isArray(last.content)
        ? last.content
        : [{ type: "text", text: last.content }];
      last.content = [...prev, ...row.content];
    } else {
      out.push({ role: row.role, content: [...row.content] });
    }
  }
  return out;
}
```

For v0.1 the BRAIN is the only writer and rows are already alternating (because of the terminator-tool pattern); `coalesce` is a no-op pass-through. The function exists from line 1 so future writers (proactive, hooks, multi-process race) don't require touching the loader.

### `src/donna/tools/send_burst.ts`

Tool definition + handler:

```ts
export const sendBurstTool: Tool = {
  name: "send_burst",
  description: `the only way to talk to the user. pass an array of strings; each
becomes a separate message the user sees. one message is fine. multiple is
fine when you have distinct thoughts that should land separately.

when to use:
- always, to talk to the user.

when NOT to use:
- when you've decided not to reply. use 'skip' instead.
- never put reasoning in here. these strings are what the user reads.`,
  input_schema: {
    type: "object",
    properties: {
      messages: {
        type: "array",
        items: { type: "string", minLength: 1 },
        minItems: 1,
        description: "one or more visible messages, in order.",
      },
    },
    required: ["messages"],
  },
};

export async function sendBurstHandler(input: unknown): Promise<string> {
  const { messages } = input as { messages: string[] };
  // delivery side-effect happens via the brain's terminator pipeline
  // (the brain reads the tool_use input and emits via the configured sink).
  // handler returns a confirmation string for the model's tool_result.
  return `sent ${messages.length} message(s).`;
}
```

Note: the handler does NOT directly print or send. Delivery is the responsibility of the terminator pipeline in `brain.ts` / the CLI, which reads `tool_use(send_burst).input.messages`. This keeps the handler pure (testable) and the sink swappable (CLI today, WhatsApp tomorrow).

### `src/donna/tools/skip.ts`

```ts
export const skipTool: Tool = {
  name: "skip",
  description: `choose silence. use when you've evaluated a turn and decided
not to reply. you must call this OR send_burst — never neither, never both.

when to use:
- a proactive turn where the moment isn't right.
- a user message that doesn't actually call for a response (e.g. "k", "ok").
  use sparingly here — most user messages deserve some acknowledgment.

when NOT to use:
- if you're going to reply. use send_burst.
- if you're stuck or unsure. say so via send_burst, don't just disappear.`,
  input_schema: {
    type: "object",
    properties: {

        type: "string",
        description: "optional one-liner for debugging logs. not shown to user.",
      },
    },
  },
};

export async function skipHandler(input: unknown): Promise<string> {

}
```

### `src/donna/brain.ts` (modified)

Two changes:

1. **Terminator-aware loop.** After running tool handlers in an iteration, check if any executed tool_use had a name in `TERMINATORS`. If yes, push the tool_results to `working` (so storage stays valid) and break the loop — do not re-enter `client.messages.create`.
2. **New return shape.**

```ts
export interface RunTurnResult {
  messages: MessageParam[];      // full updated history
  newMessages: MessageParam[];   // just messages added this turn (for persistence)
  sends: string[];               // visible sends donna emitted (empty array for skip)
  terminator: "send_burst" | "skip" | "cap_hit";  // how the turn ended
}
```

`sends` is extracted from any `tool_use(send_burst).input.messages` in the turn's working messages. For `skip`, `sends` is `[]`. If `MAX_LOOP_ITERATIONS` is hit without a terminator, `terminator = "cap_hit"`, `sends = ["sorry, got stuck in a loop. try again."]` (synthetic single-message burst — the model's last response is discarded).

`reply: string` field is removed. Callers that want a flat string can `result.sends.join("\n\n")`.

### `src/index.ts` (modified)

Startup:

1. Validate all three env vars (`ANTHROPIC_API_KEY`, `SUPABASE_DB_URL`, `DONNA_USER_ID`). Bail in voice if any missing.
2. Health-check DB: `await sql\`select 1\`` in try/catch. On failure: print `donna can't reach her memory. fix the database url and try again.` and exit 1.
3. Load history: `let messages = await loadRecentMessages(DONNA_USER_ID, 50)`.
4. Print `donna v0.1. type /quit to exit.\n`.

Per turn:

5. Read user line.
6. `const result = await runTurn({ mode: "reactive", messages, userInput: line })`.
7. On success:
    - `messages = result.messages`
    - `await saveMessages(DONNA_USER_ID, result.newMessages, "reactive")` (best-effort)
    - For each message in `result.sends`: print `donna: ${msg}` on its own line, separated by a blank line.
    - If `result.sends` is empty (skip): print nothing visible. Stderr debug: `[skip${result.terminator === "skip" ? "" : " (cap_hit)"}]`.
8. On API error: print error in voice, do NOT mutate `messages`, do NOT save.

Shutdown: `closeDb()` then `process.exit`.

## Error handling

| Failure | Handling |
|---|---|
| Missing env var on startup | In-voice error, exit 1 |
| DB unreachable on startup | In-voice error, exit 1 |
| `loadRecentMessages` fails | In-voice error, exit 1 (don't start with empty history silently) |
| `saveMessages` fails after a successful turn | Stderr "couldn't write to memory: <err>", keep in-memory `messages`, continue REPL |
| API error during `runTurn` | Caught in CLI; "donna couldn't reach the model. try again." Don't mutate `messages` or save |
| Tool handler throws | Existing path: `is_error: true` tool_result fed back, model can recover |
| `send_burst` called with empty `messages: []` | The `minItems: 1` schema constraint should prevent it; if Anthropic still emits it, treat as skip and warn in stderr |
| Loop hits cap without terminator | Synthetic single-message burst with the fallback string, `terminator = "cap_hit"` |

`saveMessages` is best-effort. While the process stays running, in-memory `messages` carries unsaved turns; on restart, they're gone (never on disk). Trade-off: keep the live REPL useful at the cost of restart-fragility on a degraded DB.

## Window size

Hard-coded constant `LOAD_LIMIT = 50` in `src/donna/memory/chat.ts`. Single source of truth. When the context builder lands later and we start summarizing older history, this constant moves into a config object.

## Forward-compat

Confirming v0.1 doesn't paint future capabilities into a corner. The recurring theme: storage is permissive, the loader normalizes for the API.

- **Async subagents.** Their internal LLM calls are isolated; never write to `chat_messages`. Dispatch and completion surface through the BRAIN as normal `tool_use` / `tool_result` blocks. Future `subagent_runs` table is additive.
- **Parallel tool execution.** Single-file refactor in `brain.ts` swapping `for...of` for `Promise.all(map(async ...))`. Persistence doesn't care.
- **Bursts that span time** (Donna sends, waits, sends again — not a single send_burst call). Future spec; today bursts are atomic from one tool call.
- **Proactive turns from background loops.** Scheduler / hook / subagent-completion writes one or more `assistant` rows with `mode='proactive'`, then triggers a BRAIN turn that loads recent history.
- **Hook-emitted messages.** Append a row with the appropriate role; the BRAIN sees it on the next load.
- **Inter-burst delays / typing indicators.** Implemented inside `send_burst`'s delivery pipeline; tool definition stays the same.

All future writers share one rule: **append rows in `seq` order; do not assume the previous row's role.**

## Testing (v0.1)

Same posture as v0: manual smoke checks. Eight gating checks.

1. **Cold start with empty DB.** Fresh Supabase project, run migration, start REPL. Should print `donna v0.1...`, history loaded as empty, no errors.
2. **Single-message reply.** Type "hi" — exactly one visible `donna: ...` line printed. Verify `chat_messages` contains 3 rows for the turn (user / tool_use(send_burst) / tool_result).
3. **Burst reply.** Prompt that should elicit multiple thoughts (e.g., "give me three reasons to drink water"). Verify Donna emits 3 separate `donna: ...` lines (one per send_burst entry). Verify `chat_messages` row N+1 has `tool_use(send_burst, {messages: [3 strings]})`.
4. **Tool then burst.** "what time is it in tokyo?" — Donna calls get_current_time, then send_burst. Verify 5 rows total (user / tool_use(get_time) / tool_result(time) / tool_use(send_burst) / tool_result(ok)). Visible output: one `donna: ...` line with the actual time.
5. **Skip.** A turn that elicits skip (e.g., user types "k" or "ok") — visible output is empty for that turn (only stderr `[skip]` line). Verify `chat_messages` shows tool_use(skip).
6. **Persistence round-trip.** Type "what time is it in tokyo?" — Donna replies. `/quit`. Restart. Type "what about london?" — Donna correctly references the prior Tokyo answer (proves history loaded) and calls get_current_time with London tz.
7. **Window cap.** Insert 60 dummy messages via SQL, restart REPL, verify only 50 most recent loaded into context.
8. **DB-down behavior.** Set `SUPABASE_DB_URL` to a bad URL, start REPL — in-voice failure and exit 1, no stack trace.

Automated tests still deferred to v1.
