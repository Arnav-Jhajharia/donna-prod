# Donna v0.1 — Supabase Persistence for Chat Messages

**Date:** 2026-05-05
**Status:** Approved (brainstorming)
**Builds on:** v0 (`v0.0.1` tag, commit `c581af7`)

## Purpose

Stop losing Donna's memory between process restarts. Persist every chat message — both directions, every turn — to Supabase Postgres. On each new turn, seed the BRAIN loop with the last N messages from the database. This is the seed of every memory backend that follows.

The CLI is the test surface today. The same persistence layer will sit behind the WhatsApp ingress when that lands.

## Non-goals

Out of scope for v0.1. Each is its own future spec.

- Async subagents and the `subagent_runs` table
- Parallel tool execution (separate single-file refactor in `brain.ts`)
- Other memory backends (Graphiti, observations, open loops, user-facts, calendar, etc.)
- Context builder blocks (USER MODEL, SITUATION BRIEF, TODAY, etc.)
- Multi-user, Supabase Auth, RLS
- WhatsApp ingress / egress
- Hooks (PreToolUse / PostToolUse)
- Proactive mode (Tier 2 / Tier 3) — schema admits it, code does not yet exercise it
- Streaming output
- A separate "conversations" or "sessions" table — there is exactly one ongoing thread per `user_id`

## Stack additions

- **`postgres@^3`** (porsager/postgres) — direct Postgres client. Tagged-template SQL, auto-prepared statements, built-in connection pooling.
- **Supabase CLI** — for migration management (`supabase migration new`, `supabase db push`).

No ORM, no schema-as-code, no PostgREST. Raw SQL files in `migrations/`, applied via Supabase CLI against the linked project.

The `SUPABASE_DB_URL` is the **session-pooler** connection string from Supabase Project Settings → Database. Format:

```
postgresql://postgres.<project_ref>:[PASSWORD]@aws-0-<region>.pooler.supabase.com:5432/postgres
```

Session pooler is correct for our long-running Node process. The transaction pooler (port 6543) is for serverless/edge environments and is not used.

## Schema

One table for v0.1:

The migration file lives at `supabase/migrations/<timestamp>_chat_messages.sql` (created by the Supabase CLI; see Migration tooling below). Its body:

```sql
create table chat_messages (
  id          uuid          primary key default gen_random_uuid(),
  seq         bigserial     not null,
  user_id     uuid          not null,
  role        text          not null check (role in ('user', 'assistant')),
  content     jsonb         not null,
  mode        text          not null check (mode in ('reactive', 'proactive')),
  created_at  timestamptz   not null default now()
);

create index idx_chat_messages_user_seq
  on chat_messages (user_id, seq desc);
```

Field notes:

- **`id`** — uuid primary key. `gen_random_uuid()` is built into Postgres 13+; Supabase runs 15+, no extension needed.
- **`seq`** — `bigserial`, monotonically increasing per insert. The actual order key. We sort by `seq desc` for "most recent first," not by `created_at`, because `created_at` can tie inside a single turn's batch insert.
- **`user_id`** — uuid. Provided via `DONNA_USER_ID` env var today. Will be derived from phone number when WhatsApp lands.
- **`role`** — `'user'` or `'assistant'`. Matches Anthropic API roles. **No alternation constraint at the storage layer** — see "Loader normalization" below.
- **`content`** — `jsonb`. The full Anthropic content array (`ContentBlock[]`), serialized verbatim. We **always normalize to array form** before storing — even a plain user string `"hi"` is stored as `[{"type":"text","text":"hi"}]`. This keeps the schema homogeneous and round-trips cleanly back into the SDK (which accepts string or array on input).
- **`mode`** — `'reactive'` for v0.1. `'proactive'` is admitted by the constraint but never written today.
- **`created_at`** — wall-clock for human-readable ordering and audit.

The compound index `(user_id, seq desc)` is what powers the load query. With one user, we don't strictly need `user_id` in the index — but the index pays for itself the moment WhatsApp ships and `user_id` becomes the dominant filter.

## Migration tooling

Supabase CLI workflow, run from repo root:

```
supabase init                         # one-time, on first setup
supabase link --project-ref <ref>     # links to the user's existing project
supabase migration new chat_messages  # creates migrations/<timestamp>_chat_messages.sql
# edit the file with the schema above
supabase db push                      # applies to the linked project
```

The actual file lands in `supabase/migrations/`, not a top-level `migrations/`, because that's where the Supabase CLI looks. We accept that path.

After this v0.1 lands, a `npm run migrate` script proxying to `supabase db push` is desirable but not required.

## Application architecture

Two new files, two modified files. No file grows beyond the Donna sizing rule (~200-400 lines).

### New: `src/donna/db.ts`

```
- exports a singleton `sql` postgres client
- lazy-initialized on first import
- reads SUPABASE_DB_URL from process.env
- exposes a single `closeDb()` function for clean CLI shutdown
- ~25 lines
```

### New: `src/donna/memory/chat.ts`

```
- exports `loadRecentMessages(userId, limit = 50): Promise<MessageParam[]>`
    - SELECT role, content FROM chat_messages
      WHERE user_id = $1
      ORDER BY seq DESC LIMIT $2
    - reverse the rows so chronological (oldest first) — Anthropic expects that
    - run COALESCE step (see Loader normalization below) before returning
    - return as MessageParam[]
- exports `saveMessages(userId, messages, mode): Promise<void>`
    - takes the new messages from the most recent turn (NOT the full history)
    - INSERT one row per message; content is JSONB-serialized
    - normalizes string content to [{type:"text", text:...}] before saving
    - does NOT coalesce; preserves one row per logical message moment
- ~80 lines
```

### Loader normalization (coalesce consecutive same-role rows)

Storage allows non-alternating rows: bursts, proactive sends from background loops, hook-emitted messages. The Anthropic API does not — `messages[]` must alternate user / assistant. So `loadRecentMessages` coalesces consecutive same-role rows by merging their `content` arrays before returning:

```ts
function coalesce(rows: ChatRow[]): MessageParam[] {
  const out: MessageParam[] = [];
  for (const row of rows) {
    const last = out[out.length - 1];
    if (last && last.role === row.role) {
      last.content = [
        ...(Array.isArray(last.content) ? last.content : [{ type: "text", text: last.content }]),
        ...row.content,
      ];
    } else {
      out.push({ role: row.role, content: [...row.content] });
    }
  }
  return out;
}
```

For v0.1 the BRAIN is the only writer and rows are already alternating; `coalesce` is a no-op pass-through. The function exists from line 1 so that bursts, proactive, and other future writers don't require touching the loader.

### Modified: `src/donna/brain.ts`

`runTurn` returns one extra field so the caller can persist exactly what was added:

```ts
export interface RunTurnResult {
  messages: MessageParam[];      // full updated history (unchanged)
  newMessages: MessageParam[];   // just the messages added this turn
  reply: string;
}
```

`newMessages` is `working.slice(args.messages.length)` — the slice from the original prefix to the end. The CLI passes that to `saveMessages` and only those rows go to the database. The model's view is unchanged.

No other behavior changes in `brain.ts`. ~3-line patch.

### Modified: `src/index.ts`

CLI startup:

1. Validate `ANTHROPIC_API_KEY`, `SUPABASE_DB_URL`, `DONNA_USER_ID` are all set. Bail with an in-voice error if any missing.
2. Health-check the DB: `await sql\`select 1\`` inside a try/catch. If it fails, print "donna can't reach her memory. fix the database url and try again." and exit 1.
3. Load history: `let messages = await loadRecentMessages(DONNA_USER_ID, 50)`.
4. Print `donna v0.1. type /quit to exit.\n`.

REPL turn:

5. Read user line.
6. `const result = await runTurn({ mode: "reactive", messages, userInput: line })`.
7. On success:
    - `messages = result.messages` (in-memory rolling history)
    - `await saveMessages(DONNA_USER_ID, result.newMessages, "reactive")` (persist new tail)
    - print `donna: ${reply}`
8. On failure: same behavior as today — print error, do **not** mutate `messages`, do **not** save anything.

CLI shutdown: call `closeDb()` before `process.exit`. Prevents hung connections on Ctrl-C.

## Error handling

The persistence layer adds three new failure modes. Each is handled explicitly.

| Failure | Handling |
|---|---|
| DB unreachable on startup (health check fails) | Bail with in-voice message, exit 1. Do not start the REPL. |
| `loadRecentMessages` fails on startup | Same as above — bail, exit 1. Do not start with empty history silently; that would lose context invisibly. |
| `saveMessages` fails after a successful turn | Log to stderr in voice ("couldn't write to memory: <err>"), keep the in-memory `messages` updated, continue REPL. Reasoning: the user already got the reply — failing the whole turn over a write error feels worse than letting the in-process session continue. The dropped rows are visible to the operator via the stderr line. Future v1+ may add a write-ahead queue. Not now. |

`saveMessages` is best-effort wrapped in its own try/catch in `index.ts`. While the process stays running, the in-memory `messages` array carries unsaved turns — Donna's view of the conversation is intact. If the process restarts before the saves recover, those turns are gone (they were never on disk). The trade-off: keep the live REPL useful at the cost of restart-fragility on a degraded DB.

## Window size

Hard-coded constant `LOAD_LIMIT = 50` in `src/donna/memory/chat.ts`. Single source of truth. When we add the context builder later and start summarizing older history, this constant moves into a config object.

50 messages = roughly 25 user-Donna exchanges (more if tools are used). For an interactive CLI, this is plenty without bloating the per-turn input token count.

## Forward-compat — what other writers need from this schema

Confirming v0.1 doesn't paint future capabilities into a corner. The recurring theme: storage is permissive, the loader normalizes for the API.

- **Async subagents.** Their internal LLM calls are isolated — they never write to `chat_messages`. The dispatch and the eventual completion both surface through the BRAIN as normal `tool_use` / `tool_result` blocks (and a future proactive turn writing assistant rows). The schema admits this with no changes; a future `subagent_runs` table is additive.
- **Parallel tool execution.** A single-file refactor in `brain.ts` swapping `for...of` for `Promise.all(map(async ...))`. The persistence layer doesn't care — `saveMessages` already handles a turn that produced multiple tool_use / tool_result blocks. They land as multiple `chat_messages` rows in `seq` order.
- **Bursts** (Donna sends multiple sequential messages from one thought). Each send is a separate row, all `role='assistant'`, in seq order. The loader coalesces them into a single API `assistant` message at load time.
- **Proactive turns from background loops.** A scheduler / hook / subagent-completion writes one or more `assistant` rows with `mode='proactive'`, then triggers a BRAIN turn that loads recent history. From the BRAIN's perspective those rows are just prior context.
- **Hook-emitted messages.** Same shape — write a row with the appropriate role, the BRAIN sees it on the next load.

All future writers share one rule: **append rows in `seq` order; do not assume the previous row's role.** The loader's coalesce step bridges to the API.

Each of these is its own future spec.

## Testing (v0.1)

Same posture as v0: manual smoke checks. The persistence layer adds three more.

End-to-end checks gating "done":

1. **Cold start with empty DB.** Fresh Supabase project, run migration, start REPL. Should start cleanly, log `donna v0.1...`, history loaded as empty.
2. **Round-trip.** Type "what time is it in tokyo?" — Donna replies. Quit. Restart. Type "what about london?" — Donna correctly references the prior Tokyo answer (proves history was loaded). She calls the tool with London tz.
3. **Tool-use round-trip.** Verify a tool_use turn persists correctly: check `chat_messages` directly via `psql` or Supabase Studio. Should see 4 rows for that turn (user / assistant-tool_use / user-tool_result / assistant-text), all with mode='reactive', `content` shape correct.
4. **Window cap.** Insert 60 dummy messages via SQL, restart REPL, verify only the 50 most recent are loaded into context (count via the SQL log line if added, or compare token cost).
5. **DB-down behavior.** Set `SUPABASE_DB_URL` to a bad URL, start REPL, expect in-voice failure and exit 1 (not a stack trace).
6. **Save-failure mid-session.** Already DB-up, mid-session kill the connection (e.g., revoke the password in Supabase). Type a turn — Donna should reply (model call still works), and a stderr warning about save failure should print. The next turn should hit the same warning. Restoring access should resume saves silently.

Automated tests still deferred to v1.
