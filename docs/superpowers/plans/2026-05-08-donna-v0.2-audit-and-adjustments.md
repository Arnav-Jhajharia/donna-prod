## Critical observations

1. **`brain.ts` already has `proactive` mode running the same loop as reactive** (it only throws on `proactive_tier3`). `runProactiveTurn` exists with a `trigger: string` shape — synthesizes a `[runtime trigger, not from the user]: …` user message. **This is a different cause shape than our spec's `<proactive_cause>` xml.** Task 10 needs to *replace* the trigger-string approach with cause-as-xml.

2. **`context.ts` uses `withTurnContext(ctx, fn)` (wrapping), not `setTurnContext`.** `getTurnContext()` throws if called outside a turn context (intentional surface-fast wiring). Plan Task 9 needs adjustment — handler imports `getTurnContext`, no need to add a `setTurnContext` setter.

3. **`delivery/proactive.ts.deliverBurstToUser` already persists to `chat_messages`.** It saves bursts as text-only `role:"assistant"` rows (not full content blocks). This is fine for the connect-script use-case (no runTurn output to persist). **For the executor we want to save the FULL runTurn newMessages (cause user-msg + assistant tool-use turn) — so the executor must NOT use `deliverBurstToUser`'s save path.** Cleanest split: extract WhatsApp-only send into a helper, executor calls saveMessages once with full newMessages and the helper for delivery only.

4. **`tools/index.ts` already has `integrationStatusTool`/`integrationConnectTool`/`integrationSetModeTool`/`integrationDisconnectTool` wired.** Task 4's tool-mode-flag needs to cover these too (status: both modes; connect/set_mode/disconnect: reactive only).
