1 · the brain today

the brain is a single function that takes a conversation and returns what to show the user. between input and output sits a tiny loop that talks to claude, runs tools, and stops when she says she's done.

the mental model

claude is a function: text in, text out. she can't do anything by herself — she can only describe what she'd like to do. the brain is what gives her hands.

think of claude as an assistant in a sealed room. she can only:

  • read whatever notes we slip under the door (the prompt + conversation)
  • slip notes back out (her response)

some of her notes are answers. others say "please check the time, then tell me what you find." those are tool calls. the brain's job is to read each note, run the action she requested, write down the result, slip it back. repeat until she says "this is the final reply for the user" — which she signals by calling one specific tool: send_burst. that's the terminator.

one turn = one user message in, one terminator out. inside that turn, claude might call ten tools or zero — the brain runs them all and only stops when she calls the terminator (or when the safety cap trips).

one turn, end to end

here's the simplest case: the user asks the time. claude needs one tool to answer, then terminates.

the pipeline

every iteration of runTurn walks the same five steps. they're named functions so each one is independently testable, swappable, and — most importantly — visible.

i buildPayload assemble the exact bytes-to-api: system + tools + history + per-turn knobs + cache markers.
ii messages.create the one network call. everything around it is local.
iii filterAssistantContent drop leaked reasoning text from claude's response before persisting.
iv dispatchToolCalls run each tool_use sequentially, wrap results as tool_result blocks.
v terminator check if a terminator was called, extract bursts and return. else loop.

the burst vocabulary — what claude can send

a burst is a list of OutboundMessage items — claude can mix freely. three texts plus a button, an image with a caption plus a list, a cta-url then a pause then a follow-up text. nine types, all rendered by the channel (cli today, whatsapp and mobile later).

typeshapeuse it for
text{type, text}default bubble. one or two sentences.
buttons{type, text, buttons:[{id,label}]}1–3 quick replies for a clear choice. never make the user type a number.
list{type, text, button_label, sections:[{rows}]}4+ choices. expand-on-tap.
cta_url{type, text, label, url}deep-link into the mobile app for actions that are better done visually.
image{type, url, caption?}chart, photo, generated image. caption is optional.
document{type, url, filename, caption?}pdf, csv, ical export.
video{type, url, caption?}any video. caption optional.
audio{type, url}voice note, audio clip.
delay{type, seconds}pause before the next bubble. 0.5–2s feels natural.

every type carries hard caps matching the strictest renderer we expect (whatsapp interactive messages). button label ≤20 chars, list rows ≤10 total, no captions inside audio, etc. these caps live in messages.ts as both the json-schema for the tool input (so claude gets a 400 and self-corrects) and a runtime validator (so malformed items get dropped, the rest of the burst still ships).

the five functions

buildPayload step i

assembles the request. nothing about it is interesting except that it exists as its own function — that's what makes npm run inspect possible. one place owns the wire format. when we add prompt caching, thinking, tool_choice, or per-turn skill overlays, they all change here.

export function buildPayload(
  messages: MessageParam[],
  config: TurnConfig = {},
): MessageCreateParamsNonStreaming {
  const system = config.systemOverlay
    ? `${SYSTEM_PROMPT}\n\n${config.systemOverlay}`
    : SYSTEM_PROMPT;

  // cache marker on the trailing tool. system + tools + this marker
  // caches; messages don't (they change every iteration).
  const tools = withTrailingCacheMarker(sdk_tools);

  return { model, max_tokens, system, tools, messages };
}

filterAssistantContent step iii safety

when claude calls a tool, her response often includes a text block before the tool_use. that text is her thinking out loud. donna's rule is that every user-visible word goes through send_burst. the pre-tool text isn't for the user. but if we persist it into history, the next turn shows claude her own scratch as if it were part of the conversation. that warps her behavior over time.

tool_useyesapi requires matching tool_use ↔ tool_result pairs

dispatchTool step iv

one tool, one call. looks up the handler in the registry, runs it, wraps the result. if it throws, the error becomes the tool result — claude sees the failure and can recover on the next iteration. a failing tool never crashes the loop. each invocation is wrapped in a langsmith span named after the tool, so traces show "get_current_time took 12ms", not "dispatchTool took 12ms."

dispatchToolCalls step iv

a single response can contain multiple tool_use blocks. this just runs them in order and collects their results. sequential, not parallel — fan-out belongs inside a dedicated sandbox tool (see §6 ptc), not inside the loop. that decision keeps the loop legible and the audit deterministic.

runTurn composer

the only function that does something end-to-end. composes the four steps above into a bounded loop. wrapped in a langsmith traceable chain so every per-iteration messages.create nests as a sub-span. capped at MAX_ITERATIONS = 10 so a runaway tool chain can't hang the process.

the contract

seven invariants the brain commits to. they're listed here so you can break them on purpose, not by accident.

  • every tool_use emitted by claude is matched by exactly one tool_result in the same turn. well-formedness.
  • the assistant content persisted into history has been filtered. raw text alongside tool_use never enters the next turn.
  • the terminator is always one of the tools in TERMINATORS. today, only send_burst.
  • the loop is bounded by MAX_ITERATIONS = 10. infinite tool chains return cleanly with terminator: null.
  • handler errors never escape runTurn. they become is_error: true tool_results, visible to claude on the next iteration.
  • the only side effects of runTurn are: the network call to anthropic, the tool handlers it dispatches, and the ledger / langsmith writes. it does not touch the filesystem, postgres, or the user — those happen in the caller.
  • per-turn knobs live in TurnConfig. defaults are constants at the top of brain.ts. granular control means the caller decides.

2 · why it's shaped this way

the brain is small on purpose. every line in it should be doing work that can't be pushed into a tool, a prompt, or a configuration.

six principles, in order of how often they bite back when violated:

one terminator, never silent

every turn ends with exactly one tool call from a known terminator set. silence (no tool call) is a bug, not a feature. by making "i'm done" a structured event, we never have to guess when to stop the loop or what to show the user.

private text vs public text are different channels

claude's free-form text is reasoning. the user-visible content lives inside the terminator's structured input. mixing the two would mean every text block is ambiguous — is this for the user or muttering? the rule lets us strip leaked thoughts safely.

history is always well-formed for the next call

tool_use blocks always have matching tool_result blocks; assistant content is filtered before persisting; thinking blocks are kept (signed, required). these aren't bookkeeping — they're prerequisites for the api accepting the next turn.

granular control means the caller decides

TurnConfig exposes model, max_tokens, system overlay, identity. when we add per-turn tool_choice, thinking budgets, or skill overlays, they go there. the brain itself has no opinions — it composes whatever the caller hands it.

composition over framework

the loop is named steps. each step is a function. swapping any one of them is a 5-line change. there's no inheritance, no plugin system, no middleware tower. when we add sub-agents we won't add a "sub-agent framework" — we'll call runTurn from inside a tool handler.

observability is first-class, not bolted on

two surfaces run every turn: a langsmith span tree (named tools, nested model calls) and a local JSONL ledger keyed by runId. npm run inspect prints the exact bytes-to-api without sending. there is no request to anthropic you cannot see locally first.

3 · the shape of more

everything else hangs off the brain as configuration plus tools. the loop stays the same. capabilities layer on by changing what's in TurnConfig, what's in the tool registry, and what other instances of runTurn exist.

four expansion vectors, in dependency order:

live layer 0 · the brain

runTurn + tool registry

a manual loop on the raw anthropic sdk. direct tools only. one model, one system prompt, one terminator. exactly what this page documented in §1.

next layer 1 · skills

capability packs that lazy-load

a skill is { systemOverlay, toolGroup, examples? }. a detector decides per turn which skills are relevant, the loader appends their overlay to the system prompt and merges their tools into the registry. the brain doesn't know skills exist.

next layer 2 · complicated tools

handlers that aren't just functions

most tools are pure functions. some are stateful: they produce drafts (typed artifacts with ids), start async work and return early, paginate large results, or compose multiple downstream calls. all of this is "still just a handler" — but the patterns are worth naming.

later layer 3 · ptc (python tool calling)

fan-out via code execution

anthropic's code_execution_20250825 beta lets claude write python that calls a curated set of our tools. used for parallel reads: "fetch last 20 emails + last 5 calendar events + open todos in one breath." the loop is unchanged — ptc is just another tool with a special sandbox.

later layer 4 · sub-agents

runTurn inside a tool handler

a sub-agent is its own configured brain — its own system prompt, its own tool list, its own terminator. called by a parent agent via a tool. the realization here is that runTurn is a primitive, not a feature: every agent in the system is an instance of it.

later layer 5 · workflows

orchestrators that compose agents over time

multi-turn coordinated flows. research → draft → review → revise → execute. each step is potentially a different agent. lives above the brain, not inside it. only worth building when we have ≥3 agents that need to talk.

the invariant across all layers: a single runTurn call is one agent's one turn. anything more complex is composed out of multiple runTurn calls, not built into the loop. the brain doesn't grow; the catalog does.

4 · skills

a skill is what claude doesn't know until you load it in.

by default claude knows english, common sense, and the tools currently in the registry. she does not know donna's domain — how we structure calorie logs, what counts as an "open loop", what the user's living profile looks like. a skill is the unit that teaches her how to do one thing and gives her the tools to do it.

what a skill is, structurally

export interface Skill {
  id: string;                       // e.g. "calorie-logging"
  systemOverlay: string;            // fragment appended to SYSTEM_PROMPT
  tools: Tool[];                      // merged into the registry for this turn
  handlers: Record<string, Handler>; // matching handlers
  examples?: ExampleTurn[];           // optional few-shot pairs
}

three pieces, doing distinct work:

  • systemOverlay — teaches the model the concepts: "a meal is composed of items. each item has kcal, protein, carbs, fat. when the user describes food, parse it into items, then log."
  • tools + handlers — gives her the actions: log_meal, lookup_food, get_daily_summary.
  • examples — optional. for ambiguous cases ("a big mac and fries" → which fries, which size). few-shot turns get injected as messages before the user input.

how a skill gets loaded

a single detector step runs at the very start of the pipeline, before buildPayload. it decides which skills are relevant for this turn. the loader then merges their overlays and tools into TurnConfig and the tool registry.

what skills are not

  • not a framework. a skill is a plain object. the loader is one function. no plugin system.
  • not a knowledge base. skills teach how, not what. user-specific facts live in memory, not skills.
  • not always on. the whole point is selective activation. a turn about "what time is it" doesn't load the calorie skill.
  • not stateful between turns. a skill is a configuration of one turn. state lives in postgres / memory.
the detector matters more than the skill format. a perfect skill catalog with a noisy detector is worse than a small catalog with a sharp one. start with three skills and a deterministic rule-based detector before reaching for an llm classifier.

5 · complicated tools

a tool handler is a function. but a function can be a lot of things — return synchronously, return an id and finish later, produce a typed artifact, paginate, compose other tools. naming these patterns helps us write them well.

five patterns worth recognizing

patternshapeexample
pure read function in, structured result out. idempotent. cheap. get_current_time, list_open_loops
pure write side effect on our own data. returns confirmation. log_meal, remember, track_open_loop
draft-producing returns an artifact + id. doesn't act on the world yet. requires an explicit follow-up tool to execute. compose_email → draftId, then execute_draft
async / deferred kicks off work, returns "queued + jobId" immediately. result delivered later via proactive turn. research, scan_inbox, generate_image
paginated returns the first slice + a cursor. claude can call again with the cursor for more. list_gmail_recent(cursor?)

drafts as first-class artifacts

the draft pattern is worth its own section because it changes how donna touches the world. any tool that's hard to undo should be split in two: one tool produces a draft (typed, ided, stored), another executes it. the user (or the main agent) approves between.

without drafts

// send the email immediately.
// no review, no cancel.
send_email({
  to: "bob@...",
  subject: "lunch tomorrow",
  body: "...",
})
→ { ok: true }

with drafts

// step 1: compose, get an id
compose_email({ to, subject, body })
→ { draftId: "draft_a1b2" }

// step 2: user approves via burst button
// step 3: execute by id
execute_draft({ draftId: "draft_a1b2" })
→ { ok: true, message_id: "msg_..." }

drafts are the bridge between plans (cheap, reversible) and acts (expensive, irreversible). they're also the thing sub-agents return when they delegate work back to the main brain — see §7 sub-agents.

async tools and proactive delivery

some work doesn't finish within one turn. research("compare these three frameworks") might take 30 seconds. claude can't sit and wait — that holds the loop. instead the tool:

  1. kicks off a background job, persists { jobId, kind, args }
  2. returns { status: "queued", jobId, eta: "~30s" } immediately
  3. worker finishes the job, writes the result to db
  4. scheduler enqueues a proactive cause with { kind: "job_complete", jobId }
  5. a fresh runTurn fires with the cause in context — donna messages the user with the result
sequenceDiagram
  autonumber
  participant U as user

async tools split the user-facing experience across two turns. the second turn is donna-initiated.

tools that compose other tools

a tool's handler can call other handlers directly. log_meal_from_alias("morning coffee") internally calls resolve_alias() then log_meal(). this is fine and often cleaner than asking claude to do both. rule of thumb: if the composition is deterministic, hardcode it inside the handler. if it requires judgment, expose both as separate tools and let claude orchestrate.

6 · ptc — python tool calling

sometimes claude needs to call five tools in parallel. ptc lets her write the python that does it, instead of we-need-five-round-trips.

what it is

anthropic's code_execution_20250825 beta. enabled via a header. when on, claude can emit a tool_use block of type code_execution whose input is python source. the api executes that python in an ephemeral sandbox. inside the sandbox, a curated subset of our tool handlers are exposed as importable functions. the sandbox prints its results; we read stdout; the loop continues.

sequenceDiagram
  autonumber
  participant C as claude
  participant L as loop (runTurn)
  participant P as python sandbox
  participant T as tools (ptc-eligible)

  C->>L: tool_use: code_execution(
"import asyncio, ...")
  L->>P: run code
  par fan out
    P->>T: gmail_search("q1")
  and
    P->>T: gmail_search("q2")
  and
    P->>T: list_calendar()
  end
  T-->>P: results (parallel)
  P->>P: aggregate, format
  P-->>L: stdout = compact summary
  L->>C: tool_result: stdout
  C-->>L: tool_use: send_burst([...])
  Note over L: terminator

three reads, one round-trip. without ptc this would be three iterations of the outer loop.

why fan-out matters

each iteration of the loop costs:

  • one model call (latency: 1–3s, tokens: full history each time)
  • tool dispatch (~ms, but sequential)

three sequential tool reads = three iterations = three model calls. with ptc, three reads happen inside one iteration's tool dispatch — one model call before, one after. latency drops by 2x; tokens drop more.

which tools are ptc-eligible

only pure reads. specifically:

  • idempotent — re-running them produces the same result
  • side-effect-free — doesn't touch user-visible state
  • cheap to serialize — results fit in the sandbox's stdout

terminators (send_burst), state-changers (log_meal, integration_connect), and stateful-by-design tools (drafts, async jobs) are never ptc-eligible. they live in the registry too, but with allowed_callers: ["direct"].

calleraccessexample tools
direct everything in the registry. claude calls these as normal tool_use blocks. send_burst, integration_connect, log_meal, get_current_time
code_execution_20250825 only the PTC_ELIGIBLE set. exposed as python functions inside the sandbox. gmail_list_recent, gmail_search, list_calendar, lookup_food

when not to use ptc

  • single tool calls. ptc adds overhead. one tool, no fan-out, just call it directly.
  • sequential dependencies. if call B depends on call A's result, sequential outer-loop iterations are clearer.
  • writes or terminators. see above. these change user-visible state and must be auditable in the main loop.
the loop is unchanged. ptc is just a tool in the registry whose handler is "ask anthropic to run python in a sandbox." everything downstream — filterAssistantContent, dispatchToolCalls, the terminator check — operates identically.

7 · sub-agents

runTurn is a primitive, not a feature.
every agent in the system — main, drafter, researcher, expert — is the same function with different configuration. a sub-agent is what happens when one tool handler calls another runTurn.

the realization

look at runTurn's signature. it takes messages, returns sends + new messages + a terminator. it doesn't care about ingress, persistence, who started the turn. anyone can call it. including a tool handler.

this means the brain naturally composes. a parent agent can delegate by calling a sub-agent's runTurn from inside a tool. the sub-agent has its own system prompt, its own tool registry, its own terminator — but it's the same loop, the same observability, the same contract.

// the realization, as code:
export interface AgentConfig {
  system: string;
  tools: Tool[];
  handlers: Record<string, Handler>;
  terminators: Set<string>;
  model?: string;
  maxIterations?: number;
}

// the existing runTurn is one instance:
export const mainAgent: AgentConfig = {
  system: SYSTEM_PROMPT,
  tools: [getCurrentTimeTool, sendBurstTool],
  handlers: { get_current_time, send_burst },
  terminators: new Set(["send_burst"]),
};

// a sub-agent is just another instance:
export const emailDrafter: AgentConfig = {
  system: EMAIL_DRAFTER_PROMPT,
  tools: [getContactTool, produceDraftTool],
  handlers: { get_contact_email, produce_draft },
  terminators: new Set(["produce_draft"]),
};

// runAgent generalizes runTurn:
export async function runAgent(
  agent: AgentConfig,
  messages: MessageParam[],
  config: TurnConfig = {},
): Promise<AgentResult> { /* identical to today's runTurn */ }

// today's runTurn becomes a one-liner:
export const runTurn = (m, c) => runAgent(mainAgent, m, c);

different brains have different terminators

the main brain terminates on send_burst — its job is to talk to the user. a drafter brain terminates on produce_draft — its job is to make a typed artifact. a researcher brain terminates on compile_brief — its job is to write a structured summary.

generalizing the terminator unlocks the entire pattern. the terminator is the agent's product.

four canonical sub-agent shapes

the executor

do work, return result

delegated task, completes within the parent's turn. parent passes args, sub-agent does the work, returns a result. like a normal function call but with claude's judgment inside.

terminator: return_result with structured payload

the drafter

propose, await approval

produces a typed artifact (email draft, calendar invite, expense entry) and returns its id. parent surfaces the draft for approval; a later turn executes by id.

terminator: produce_draft → draftId

the researcher

deep work, return brief

runs many tool calls, often async. consumes long context. compresses the answer into a brief. parent gets a structured summary, not the raw transcript.

terminator: compile_brief → markdown + sources

the expert

domain specialist

narrow scope (calorie reasoning, calendar wrangling, expense categorization). own prompt, own tools, own examples. called when a domain question is too detailed to clutter the main prompt.

terminator: domain-specific structured return

worked example: "email bob about lunch tomorrow"

this is the poke-style drafter pattern, in our shape. two turns: turn 1 produces a draft and surfaces it; turn 2 (triggered by the user tapping a button) executes.

nesting in the loop, in detail

here's what happens during turn 1, iteration 0 of the main agent:

  1. main agent's buildPayload assembles the request with the main system prompt and a tool list that includes delegate_email_drafter.
  2. claude responds with tool_use: delegate_email_drafter({task: "email bob about lunch tomorrow"}).
  3. dispatchTool invokes the handler. the handler isn't a leaf — it calls runAgent(emailDrafter, [{role:"user", content: task}]).
  4. now a nested runTurn runs. the drafter's prompt is loaded, its tools (get_contact, produce_draft) are exposed, its loop iterates. it calls get_contact_email("bob"), then produce_draft(...). produce_draft is the drafter's terminator — the nested loop exits with the draft as its product.
  5. the handler returns the draft (id + preview) to dispatchTool, which wraps it as a tool_result.
  6. the main agent's next iteration sees the result. claude decides to ask the user for approval — calls send_burst. terminator. turn 1 done.

what each agent sees, in its system prompt

main agent

"you are donna. talk to the user.
when they ask you to email someone:
1. call delegate_email_drafter(task)
2. surface the draft with buttons
3. on approval, execute_draft(draftId)

email drafter sub-agent

"you draft emails. you do not send.

1. look up the recipient (get_contact_email)
2. compose subject and body

observability across the nest

each runAgent call generates its own runId and ledger trail. the parent's tool dispatch logs a tool_calls event for delegate_email_drafter; the sub-agent's run gets stamped with parent_run_id. in langsmith, the sub-agent's spans nest under the parent's tool span. in the JSONL ledger, both runIds coexist; grep parent_run_id=<id> shows the whole tree.

when not to use a sub-agent

if it's...do this instead
a deterministic computationa plain tool with a tight handler
parallel readsptc fan-out (§6)
swapping the prompt for one turna systemOverlay via TurnConfig
teaching a domaina skill (§4)
any case where the parent agent can handle it itselflet it. sub-agents are expensive — extra model calls, extra context.

sub-agents earn their place when the work needs a different prompt, a different terminator, or a different tool set. anything less, keep it flat.

8 · the tool layers

every "thing donna can do" is a tool. but tools come in tiers — direct, ptc-callable, sub-agent-wrapping, skill-gated. picking the right tier for a capability is the most consequential design choice in the catalog.

four tiers, in increasing complexity

tiershapewhen to reach for it
direct tool live a function in the registry. claude calls it via tool_use. handler runs in process. result returned synchronously. default. if it's a discrete, well-defined action, start here.
ptc tool layer 3 also a direct tool, but marked allowed_callers: ["code_execution"]. claude can call it from inside python sandbox code for fan-out. pure read, called often, often called in groups. promotes from direct → ptc as patterns emerge.
sub-agent tool layer 4 a tool whose handler runs runAgent(otherAgent, ...). parent sees one tool call; nested loop does the work. different prompt, different terminator, different tool set. drafts, deep research, domain experts.
skill-gated tool layer 1 a direct tool that's only in the registry when its skill is loaded. selective exposure. large catalogs. teaches claude when each tool applies via the skill overlay; avoids prompt bloat.

the same job, four tiers — a comparison

imagine the capability is "summarize my unread email." here's how it looks at each tier:

direct tool

summarize_inbox()

one handler. inside, it fetches recent emails, formats a summary, returns markdown. simple, fast, fixed shape.

cost: 1 model call · latency: 1× tool
ptc fan-out

multiple read tools
orchestrated by claude

claude writes python that calls gmail_list_recent, gmail_search("important"), and get_unread_count in parallel. she summarizes the combined result.

cost: 2 model calls · latency: max(tool_a, tool_b, tool_c)
sub-agent

inbox_triage
specialist

its own prompt: "you triage inboxes." its own tools. its own multi-step logic (categorize, prioritize, score). returns a typed brief.

cost: 2+ model calls · latency: full nested loop · gain: better judgment

the right tier depends on the size and judgment of the task. "summarize my unread email" is probably a direct tool. "go through my inbox and tell me what's important and draft replies" is a sub-agent.

10 · roadmap

ordered by what unlocks what. don't jump ahead. each step earns the next.

  1. prompt iteration. with the new outbound vocabulary live, refine the system prompt until claude's choices (text vs buttons vs cta_url vs list) feel right across a wide range of user inputs. nothing built downstream matters if her voice and judgment aren't there.
  2. postgres + users + chat_messages. persistence. lift the schema from the ts archive almost as-is. now history survives a restart and we can run more than one user at a time.
  3. MemoryStore (pgvector). one interface — remember(fact) / recall(query) / recallRecent(n). expose as two tools. start small. resist the urge to build five backends.
  4. ContextBuilder. when raw history starts hitting token caps, this is the layer that decides what enters the payload. budget-aware, retrieval-aware. until then, messages is enough.
  5. refactor: runTurn → runAgent. generalize the loop to take an AgentConfig. the existing main brain becomes one config. nothing user-visible changes — but every layer below this point becomes trivial.
  6. first sub-agent: the email drafter. the poke-style drafter pattern. teaches us the nesting, the draft artifact, the approve-and-execute flow. small enough to ship.
  7. skills (loader + first three). calorie logging, calendar wrangling, inbox triage. each is one overlay + a tool group. rule-based detector first.
  8. ptc. add the code_execution_20250825 tool. promote read-heavy tools to PTC_ELIGIBLE. the gain is latency on fan-out.
  9. second + third sub-agents. researcher (long-running, async). expert (e.g. expense categorizer with its own examples).
  10. mobile delivery + native rendering. the OutboundMessage shape is already there; the mobile renderer is just a new channel.
  11. proactive runtime. schedule + arbiter + executor. now runTurn can fire from a cron with mode: "proactive" in the system overlay. cleanly composed on top of everything below.

11 · the discipline

the brain stays small because we say no a lot. these are the things we won't do, and the bar each addition has to clear.

what we won't do

  • no framework. not langgraph, not autogen, not crewai. we just left one framework so we could see every byte. we won't pick up another.
  • no nine memory backends on day one. the python archive had nine. we'll start with one (pgvector) and add backends only when we've felt the actual limitation.
  • no shadow attention promoter. the python promote.py cycle is interesting but expensive. proactive earns its way in via a simple schedule + arbiter — not a confidence-decayed shadow queue.
  • no implicit pre/post hooks. handlers are functions, not pipelines of plugins. if a handler needs to write to memory, it imports the memory module — it doesn't get magicked in by a hook system.
  • no compatibility shims. when we change the shape of RunTurnResult or OutboundMessage, we change every caller. no v2() functions, no migration stubs.
  • no "what if we someday" abstractions. three similar lines beat a premature interface. when there are five, we abstract.

the bar each addition must clear

  1. can it be a tool first? if yes, do that. tools are the cheapest addition.
  2. does it earn its complexity? a sub-agent costs an extra model call per turn. a skill costs prompt tokens. justify the cost with the gain.
  3. can the user see it work? features that don't show up in the burst, or in npm run inspect, or in the ledger, are invisible. invisible features rot.
  4. will it survive the next rewrite? if the next person looking at this code wouldn't keep it, it's debt. write it like you're the one reading it again next quarter.
the brain stays small because every line in it should be doing work that can't be pushed into a tool, a prompt, or a configuration. when we feel the urge to add to brain.ts, the first question is: can this live as a tool? as a handler? as a skill? almost always, yes.
