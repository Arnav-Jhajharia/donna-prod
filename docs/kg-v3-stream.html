option 3 of 3

moments stream. the day is a query.

there is no events table and no entries table — there is one table of moments. a moment is anything that happened at a time. the day is what falls in a date range. simplest mental model. most uniform write path.

1. thesis

"events vs entries" is a false dichotomy. they're the same thing observed at different abstraction levels. collapse them.

a user's life through donna is a time-series of moments. some are raw (a message arrived). some are inferred (donna noticed user sounded flat). some are donna's own actions (a notification sent at 5pm). all share one shape: when, who, what, payload.

"the day" is not a row. it is a query — moments where date = today. "this week's commitments" is a query. "every interaction with sarah" is a query. the data model holds moments. composition does the rest.

moments — the only table that matters

{
  id           uuid pk,
  user_id      uuid not null,
  ts           timestamptz not null,
  date         date generated always as ((ts at time zone tz)::date) stored,
  origin       origin_enum not null,    -- observed | inferred | acted
  source       source_enum not null,    -- whatsapp | imessage | gmail | cal | donna | system
  actor        actor_enum not null,     -- user | donna | system | external
  kind         text not null,           -- 'message' | 'commitment' | 'meeting' | 'donna_notification' | ...
  body         text,                    -- denormalized searchable text (pgvector)
  payload      jsonb not null,
  entity_refs  uuid[] not null default '{}',
  supersedes   uuid references moments(id),  -- corrections
  caused_by    uuid references moments(id),  -- linkage between related moments
  created_at   timestamptz default now()
}

-- partitioned by (user_id, date)
-- indexes:
--   (user_id, date, ts)
--   (user_id, kind, date)
--   (user_id, entity_refs gin)
--   (body) using pgvector

origin — the key abstraction

originmeaningexample
observeddirectly witnessed by donnaa whatsapp message, a gmail thread arrived
inferredderived by donna from observed moments"user sounded flat" — points back to evidence via caused_by
acteddonna did this herselfnotification sent, reminder fired, tool called

this trichotomy is the only structural distinction. observed moments are truth — never deleted, never mutated. inferred moments are donna's interpretations — can be superseded if extraction improves. acted moments are donna's history — what she did, when, why.

3. write path

flowchart LR
  M[message / integration / donna action] --> W[write moment
origin=observed or acted]
  W --> M1[(moments)]
  M1 --> EX[extractor]
  EX --> M2[write moments
origin=inferred]
  M2 --> M1
  M1 --> GR[update entities + edges]
  CRON[nightly] --> SEAL[write day_narrative]
  CRON --> RHY[update rhythms]
  1. everything observable or done becomes a moment immediately. one write path.
  2. extractor reads moments, may emit more moments (origin=inferred) with caused_by pointing at sources.
  3. graph updates as a side effect of moments touching entities.
  4. nightly: narrative + rhythm recomputation.
no separate "events vs entries" debate. a commitment is a moment. the message that contained it is a moment. donna's reminder firing is a moment. they all share a table, differ only in kind and origin.

4. read path

standard per-turn bundle

-- today, in order
SELECT * FROM moments
WHERE user_id = $1 AND date = today
ORDER BY ts;

-- recent narrative ambience (last 7 days)
SELECT date, summary, energy FROM day_narrative
WHERE user_id = $1 AND date BETWEEN today-7 AND today-1;

-- entities mentioned in current turn → 1-hop graph
SELECT n, e FROM entities n
JOIN edges e ON (e.src = n.id OR e.dst = n.id)
WHERE n.user_id = $1 AND n.id = ANY($2);

-- patterns for this day-of-week
SELECT * FROM rhythms WHERE user_id = $1 AND dow = today_dow;

one of the wins: a single tool surface scales. as donna learns new tricks, new questions, new patterns — they're all just queries against moments. you don't add new tables, you add new queries.

5. worked example — the 5pm dentist nudge

sequenceDiagram
  participant U as user
  participant D as donna
  participant M as moments

  U->>D: "remind me to book the dentist tomorrow"
  D->>M: moment(kind=message, origin=observed, actor=user)
  D->>M: moment(kind=commitment, origin=inferred, caused_by=^, payload={what, due:tmr 5pm})
  D->>M: moment(kind=mention, origin=inferred, entity_refs=[dentist], caused_by=^^)

  Note over D,M: 5pm today
  D->>M: moment(kind=donna_notification, origin=acted, actor=donna, caused_by=commitment_id)
  D->>U: "did you book the dentist?"

  U->>D: "yeah, booked for next tue"
  D->>M: moment(kind=message, origin=observed)
  D->>M: moment(kind=meeting, origin=inferred, payload={title:dentist, when:next_tue})
  D->>M: moment(kind=commitment_resolved, origin=inferred, supersedes=commitment_id)

three weeks later: moments WHERE date='2026-05-21' AND kind='donna_notification' AND entity_refs @> '{dentist_id}' returns donna's nudge. one query. one table.

6. rhythms — patterns emerge from one table

nightly job groups moments by user × day-of-week × kind × normalized signature. counts recurrences, computes confidence, writes rhythm rows. because everything lives in moments, this is a single SQL pass — no joining across event/entry tables.

-- gist of the rhythm detection
SELECT
  user_id,
  extract(dow from date) as dow,
  kind,
  normalize_signature(payload) as sig,
  count(*) as n,
  mode() within group (order by extract(hour from ts)) as hour
FROM moments
WHERE user_id = $1
  AND ts > now() - interval '60 days'
GROUP BY 1,2,3,4
HAVING count(*) >= 4;

7. tradeoffs

good at

  • mental simplicity — one table, one shape, one tool family
  • cross-day queries are native, not orchestrated
  • pattern detection lives where it should — over the stream
  • fewer schema decisions over time (just add a kind)
  • provenance chain via caused_by is explicit

costs

  • discipline lives in conventions, not types (kind enum, payload shapes)
  • one massive table — partitioning matters early
  • truth vs interpretation lives in origin column, not separate tables
  • replay = "supersede inferred moments" — subtler than dropping a table
  • hard to enforce schema on payload jsonb without convention

8. when to pick this

pick this if you believe donna's value comes from cross-time pattern recognition, not isolated day-rollups. it's the cleanest model conceptually — and the closest to how donna actually thinks ("what has this person done across many moments"), but demands schema discipline you can't get from the database alone.

opt 1 trades this for stricter types. opt 2 trades it for stricter replay purity.
