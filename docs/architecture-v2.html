the architecture.

one brain, three surfaces. donna runs the same runTurn for every text the user sends and every nudge she chooses to send, regardless of where the user lives that moment. whatsapp, the mobile app, the voice call, the cli. below: every box, every wire, every flow.

1 · the thesis

donna is one person's assistant. one brain, recoverable across three surfaces, with a shared identity and a shared history. the architecture exists to make "donna on whatsapp" and "donna in the app" and "donna on a call" indistinguishable to the user, and trivially small to extend when a fourth surface lands.

two invariants the architecture must keep. (a) the brain is a pure function of history + tools; surfaces don't leak into it. (b) identity is unique per human, not per channel. one user, one row, all surfaces.

3 · surfaces

four user-facing entry points today. each speaks its own protocol on the wire, all four converge on a single runTurn invocation.

live cli

the cli

readline loop in src/index.ts. user types, brain replies inline. only surface that runs the brain in-process. used for daily dogfooding of brain changes. trigger fires render inline too.

wip whatsapp

whatsapp

meta cloud api. inbound webhooks land at /api/whatsapp, parsed for the user's phone (e.164 sans +), resolved via getOrCreateUserByPhone, dispatched to the brain. outbound bursts post back to the meta cloud api. ingress + delivery code in src/donna/ingress/whatsapp.ts; archive-era delivery layer being ported.

wip mobile

mobile app

expo + react native + clerk (apple sign in). text loop posts to /api/mobile with the clerk jwt; server reads getAuth(c).userId, resolves to a donna user, dispatches the brain. proactive nudges + voip calls land via apns from the server. ingress in src/donna/ingress/mobile.ts.

later voice

voice (callkit)

third surface. server fires voip push via apns; ios shows callkit; the app joins a livekit room; the voice agent (separate process) bridges deepgram stt → brain → sesame csm tts. all the wiring is committed (voice/, src/donna/voice/); production readiness pending.

later imessage

imessage

archived from prior iteration. shape is identical to whatsapp (inbound webhook → resolve by phone → brain). resurrects when we want it; not on the current track.

later web

web dashboard

design exploration lives in a sibling repo (~/donna/dashboard/) — next.js + framer-motion + the design tokens the mobile app mirrors. not wired to the brain today.

4 · the server

one hono process, four mounts. clerk middleware runs on every request so authenticated routes can pull userId straight off the context.

// src/server.ts (shape)
const app = new Hono();
app.use("*", clerkAuth);

app.get  ("/health",       (c) => c.text("ok"));
app.route("/api/whatsapp", whatsapp);   // meta cloud webhook
app.route("/api/mobile",   mobile);     // clerk-authed text loop
app.route("/api/pairing",  pairing);    // code claim
serve({ fetch: app.fetch, port });
routeauthpurpose
GET /healthnonerailway liveness check. returns ok.
POST /api/whatsappmeta verify token + signatureinbound whatsapp messages. parses payload → user_id by phone → brain dispatch → reply.
POST /api/mobileclerk jwtinbound from the app. getAuth(c).userId → resolve via clerk_id → brain dispatch → json response (and/or push).
POST /api/pairingclerk jwt (request), none (claim)mobile asks for a 6-digit code; whatsapp message claims it; server links the two surfaces to one user.
why hono. small, type-safe, runs unchanged on node / bun / cloudflare. the archive used raw node:http which forces you to write your own router. hono is the modern minimal.

6 · proactivity (triggers)

proactivity is the same loop running unprompted. a trigger is a stored intent (action text + fire time); when it fires, the runtime synthesises a user-shaped turn carrying that intent and runs the brain. no new code path, no separate "proactive" engine — just a different cause for the same effect.

shape

// triggers/store.ts (sketch)
type Trigger = {
  id: string;
  action: string;        // "remind me about sara"
  fire_at: Date;         // when
  status: "pending" | "fired" | "cancelled";
  user_id?: string;      // per-user when multi-tenant
};

// triggers/runtime.ts
setFireHandler(async (t) => {
  if (!markFired(t.id)) return;
  history.push({ role: "user", content: t.action });
  const result = await runTurn(history);
  for (const msg of result.sends) await render(msg);
});

what the model can do with triggers

toolaction
create_triggerschedule an action: "remind me at 3pm to call mom".
list_triggerspeek at what's pending.
cancel_triggercancel by id.

today vs tomorrow

  • today: in-memory store. survives only as long as the cli/server process lives. fire handler routes to the cli's render.
  • next: persist triggers to postgres so they survive restarts. cron-like reattach on boot (re-arm pending triggers).
  • then: per-channel delivery — fired trigger picks the user's preferred surface (whatsapp default) and ships the burst through the right delivery layer.

connection shape

// src/donna/db.ts
const sql = postgres(DATABASE_URL, {
  prepare: false,                       // supabase transaction pooler doesn't allow prepared
  transform: { undefined: null },       // js undefined → SQL NULL
});
export const db = drizzle(sql, { schema });
two pooler ports. port 6543 = transaction pooling (runtime). port 5432 on the same pooler host = session pooling (introspection, anything needing prepared statements). drizzle-kit needs the latter for db:pull; runtime stays on the former.

10 · the identity model

one human, one row in users, multiple lookup keys. phone is the whatsapp/imessage key; clerk_id is the mobile key. either may be null until the user binds that surface. the linker (getOrCreateUserByClerk, paired with the mobile ingress) merges identities when both become known.

the table

create table users (
  id          uuid primary key default gen_random_uuid(),
  phone       text unique,               -- nullable. whatsapp / imessage key.
  clerk_id    text unique,               -- nullable. mobile app key.
  profile_name text,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

three install permutations

scenarioresolution path
whatsapp firstinbound webhook → getOrCreateUserByPhone(phone) → row created with phone set, clerk_id null. all whatsapp turns dispatch this user_id.
then installs appapple sign-in via clerk → mobile posts to /api/mobile with jwt → server reads userId via clerk middleware → linker reads phone from clerk's user profile → finds existing whatsapp row by phone → attaches clerk_id to that same row. one user, two keys.
app firstapple sign-in → clerk has no phone yet → onboarding asks the user to verify phone via the whatsapp pairing flow → on claim, server attaches phone to the existing app row. one user, two keys.
why phone is the spine. the whatsapp surface has nothing but a phone to identify the user. mobile has clerk_id but onboarding is in our control. designing around "phone first, link second" lets the dumbest surface still create users.

15 · flow · proactive trigger

donna decides during a chat that she needs to come back later. she calls create_trigger with an action and a fire time. when the time hits, the runtime synthesises a turn carrying that action.

sequenceDiagram
  autonumber
  participant U as user
  participant B as brain
  participant T as triggers/runtime
  participant Ch as channel (cli today)

  U->>B: "i'm gonna nap, wake me in 20"
  B->>B: create_trigger({ action: "nap is over...", fire_at: now+20m })
  B->>T: store + setTimeout(20m)
  B->>U: "go rest. i'll text in 20."

  Note over T: 20 minutes pass

  T->>T: setTimeout fires
  T->>T: markFired
  T->>B: runTurn(history + { role: "user", content: "nap is over, gently nudge them awake." })
  B-->>Ch: { sends: [{ type: "text", text: "you up?" }] }
  Ch->>U: render burst
same loop, different cause. the brain doesn't know the trigger fired — it sees a normal user-shaped turn. the only thing the runtime adds is the synthesis of the user message from the trigger's action text. this means anything the brain can do reactively, she can do proactively. no second engine.

17 · the discipline

the architecture is small on purpose. one brain function, one server, one db, one schema, one identity table. each surface is a thin translator between its native protocol and the brain's (history) → (sends) contract. when adding a thing feels like it needs three new abstractions, the answer is usually one new tool plus a fallback string.

the rules we keep

  • the brain doesn't know what surface called it. no if (channel === "whatsapp"). ever.
  • one human, one row. identity merges across surfaces; chat history is keyed by user_id, not channel.
  • send_burst is donna's only voice. raw text outside of it is private to the model.
  • triggers reuse the brain's loop. proactivity is not a separate engine.
  • tools are small, focused, and self-describing. the description tells the model when to call it — write for the model, not for you.
  • everything cacheable gets cached. system prompt and tool definitions sit before the cache breakpoint; history grows after.
  • persistence is one schema, one source of truth. migrations in supabase/migrations/. types regenerated via npm run db:pull.
