1 · the shape: three tiers

poke is not one model with one prompt. it's a stack of three roles, each its own agent with its own prompt:

flowchart TD
  U([user — whatsapp / imessage])
  P[poke
personality · voice · what the user sees]
  E[interaction agent
"execution engine" · no direct user access]
  S1[search-agent]
  S2[notion-agent]
  S3[linear-agent]
  S4[browser-agent]
  S5[...]

  U <--> P
  P -->|task request| E
  E -->|result + ids| P
  E --> S1
  E --> S2
  E --> S3
  E --> S4
  E --> S5

poke filters and frames. the execution agent searches, drafts, and acts. specialist sub-agents do the actual integration work.

the seam between them is structural:

poke
the only thing the user ever talks to. holds voice and identity. decides what to surface.
execution agent
receives task requests from poke. has no direct user access. returns structured results upward — ids, summaries, no opinions.
sub-agents
spawned via a task tool. given a goal, not instructions. parallel by default.
house rule, repeated everywhere: never expose this seam to the user. no mention of tool names, agents, or workflows. the persona is unified by policy, not by architecture.
your final output is directed to poke, which handles user conversations and presents your results to the user. focus on providing poke with adequate contextual information; you are not responsible for framing responses in a user-friendly way. agent.md — opening

2 · proactivity = triggers

poke's "acts before you ask" magic isn't a background reasoning loop. it's the agent planting natural-language instructions for its future self. two kinds:

typefires oncalled to the user
crona time (cron expression, once or repeating)"reminder"
emailan inbound email matching a condition"automation"

each trigger carries an action field — a free-text instruction. when the trigger fires, the execution agent runs again with that action as its prompt. the prompt itself says:

when creating triggers, you should always be specific with the action. an agent should be able to unambiguously carry out the task from just the action field. as a good rule, trigger actions should be as detailed as your own input. agent.md — triggers

triggers compose

the killer example is verbatim in the prompt — "poke jony about the project if he hasn't responded in 10 minutes":

sequenceDiagram
  autonumber
  participant U as user
  participant P as poke
  participant E as execution agent
  participant T as trigger store
  participant J as jony (email)

  U->>P: poke jony if no reply in 10min
  P->>E: set up the "chase jony" behavior
  E->>T: create cron trigger (T+10min)
action: "email jony, then cancel the email trigger"
  E->>T: create email trigger
condition: "jony responded"
action: "cancel the cron trigger"
  E-->>P: triggers set, ids: ...
  P->>U: i'll chase him at 4:23 if he's quiet

  alt jony replies before T+10
    J-->>T: inbound email
    T->>E: fire email trigger
    E->>T: cancel cron trigger
    E-->>P: jony replied, chase cancelled
    P->>U: jony got back to you — handled
  else 10 minutes pass
    T->>E: fire cron trigger
    E->>J: send email asking for status
    E->>T: cancel email trigger
    E-->>P: sent the nudge to jony
    P->>U: nudged him just now
  end

the user only ever talks to poke. the "magic" isn't a new turn shape — it's a normal request where the agent's action happens to include planting two natural-language instructions for future-self. no scheduler service, no race conditions in code.

this is the single most important pattern in the prompt. proactivity collapses to: a tool to create natural-language todos for future-you, and a runtime that re-invokes you with them. everything "ambient" about poke is built on this primitive.

3 · the draft / confirm dance

poke never sends an email or creates a calendar event directly. the flow is rigid:

sequenceDiagram
  autonumber
  participant U as user
  participant P as poke
  participant E as execution agent

  U->>P: email bob about lunch
  P->>E: compose email to bob, lunch
  E->>E: compose_draft({...}) → draftId
  E-->>P: draftId
  P->>U: display_draft(draftId)
  Note over U: user sees draft + 👍/👎
  U->>P: 👍
  P->>E: execute_draft(draftId)
  E-->>P: sent
  P->>U: done.

same machine for replies, forwards, calendar events, updates, deletions. drafts have ids that persist across agents — poke can show a draft the execution agent composed. confirmation accepts text ("yes") or emoji (👍 ❤️ 🎉 all count as yes; 👎 😡 ❌ count as no).

when confirming any email drafts with the user, you MUST output them as a call to display_draft. agent-protocol.md

4 · memory: invisible by rule

the memory-guidelines file is short, and its rule is essentially:

  • memory is automatic — no explicit save action
  • long conversations get summarized and re-injected as context
  • users cannot see memory summaries or system notes
  • never mention memory to the user — should feel like continuation, not retrieval
  • if a detail isn't in current context, prefer an educated guess from what's known over asking the user to repeat themselves

this is the opposite of chatgpt's "memory updated" toast. poke wants the illusion of a person who just remembers.

conspicuously absent: no mention of embeddings, vector stores, semantic search, or retrieval. memory in the prompts looks like plain-text summary + context window. (could be off-prompt infra. striking that it's not even hinted at.)

5 · the tappable-link trick

whatsapp and imessage are plain text. poke needs rich, tappable actions inside that text. the solution is a hardcoded link-label convention:

[28_view-email](poke.com/email/abc123)
[02_accept](poke.com/draft/xyz789)
[29_track-order](poke.com/order/...)

there are 29 approved labels, numbered 01_view-details through 29_track-order. the client renders each label as an emoji shortlink — so what arrives in the user's bubble is a clickable emoji button, not the raw label string.

this is how poke gets a button-y interactive ui inside a channel that fundamentally only supports text.

6 · channel awareness

baked into the prompt, not handled at the transport layer:

poke can only send free-form messages within 24 hours of receiving a user message. outside this timeframe, responses must use pre-approved templates that lack natural conversational qualities. platform-guidelines.md

this is whatsapp's business-messaging policy. poke can't engineer around it, so it prompts around it: if the 24h window is closed, the agent is told to transparently explain the limitation and suggest switching to imessage or sms. the model itself is the workaround.

emoji-as-confirmation is also a platform affordance — see §3.

7 · output discipline

the seam between execution agent and poke is enforced by formatting rules. the execution agent's output is for poke to read, not for the user to read:

  • no preamble or postamble ("here's what i found…", "let me know if…")
  • no analysis, no opinion — just relay facts and ids
  • always include the right id: emailId, draftId, attachmentId, triggerId — never userId
  • never use the generic word id
  • no caps, no bold, no italics for emphasis
  • wrap lists in code tags so whatsapp doesn't mangle them

the personality lives upstairs in poke. the execution agent is deliberately voiceless.

8 · sub-agent prompting style

a real opinion lives in the prompt, and it's worth quoting:

when using the task tool, only communicate the goal and necessary context to the agent. avoid giving explicit instructions, as this hinders agent performance. ensure the provided goal is sufficient for correct execution, but refrain from additional direction. agent.md — sub-agents

sub-agents are treated as autonomous executors, not functions. you tell search-agent what you want to find, not how to find it. this is a strong bet: that giving a capable model a goal + context beats trying to script its tool calls.

parallel-by-default everywhere:

when in doubt, run multiple searches in parallel rather than trying to guess the "most appropriate" source. agent.md — integrations

if a query could hit notion or email, hit both at once. don't pre-optimize. let the cheap call resolve the ambiguity.

9 · the exfil vector

the reason these files exist: someone got poke to email out its own system prompts. the email tooling — compose_draft, execute_draft, plus the email-triggered automation system — turned into a self-prompt-injection vector. a crafted inbound email, parsed by an agent that can also send_email on the user's behalf, can ask the agent to send the prompt as the body.

relevant to donna: the moment donna can send a message as the user — email, whatsapp template, anything — based on conditions another party can influence (inbound mail, ingested content, third-party tool output), the same class of leak is possible. the failure mode is not "model said something weird"; it's "model carried out a clear-text instruction it shouldn't have trusted as user intent."

10 · what's notably absent

things i expected to find and didn't:

  • no rag. no embeddings, no vector store, no semantic search anywhere in the five files i have. memory is plain-text summary + context.
  • no persistent sub-agent identity. each task call looks stateless. no "talk to the search-agent you used last time."
  • no trigger conflict resolution in policy. two contradictory triggers will both fire unless one cancels the other. the agent is expected to plant cancellations as it plants the triggers (the jony example).
  • no autonomous reasoning loop. no "wake up every n minutes and think about the user." proactivity comes entirely from triggers the agent itself plants, in response to user requests.
  • no pricing or model selection in-prompt. referenced in press as ~$50/user/month in inference; nothing in the prompts about which model handles which tier.

the missing pieces could live in the two unread files (guidelines.md, integration-policies.md) or off-prompt. worth flagging as gaps, not as facts.

11 · for donna

what's worth borrowing, what's worth refusing:

borrow

  • triggers-as-natural-language. the "trigger action = future prompt to self" primitive is genuinely elegant. donna's proactive layer should look more like this and less like a cron worker.
  • self-cancelling trigger pairs. the jony pattern (cron + email, each cancelling the other) is the right shape for "follow up if no reply."
  • draft / confirm with emoji. rigid state machine, low surprise, plays nicely with bursty voice.
  • parallel-by-default tool calls. already a habit, worth keeping explicit.
  • id discipline. never id; always the typed name.

refuse

  • three-tier agent split. poke needs it because voice and execution are at war (whatsapp templates, persona unification across many integrations). donna's voice is the product — the burst contract already lives at the leaf. one engine, one voice, no execution-engine intermediary.
  • memory as "automatic and invisible." per feedback_donna_memory_own_layer — donna owns memory as the product. it's not a hidden convenience; it's the thing you're paying for. memory may surface (gently) when it's load-bearing.
  • whatsapp 24h workaround. imessage-first. don't inherit a regulatory wart that isn't ours.
  • "give sub-agents a goal, not instructions." tentatively keep, but donna's tools are small and few. premature autonomy is just "model wanders." revisit when there are real sub-agents.

watch for

  • the exfil vector. the day donna sends mail/messages as the user based on inbound content, the same class of leak applies. design the send path with a hard human-in-loop confirmation for anything sourced from non-user input.
