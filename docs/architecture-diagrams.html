5. scheduler + executor

everything proactive is a scheduled brain run with a cause. one table (donnaschedule), one cron tick, one entrypoint. trigger types differ only by cause_kind.

sequenceDiagram
  autonumber
  participant T as ticker (setInterval 30s)
  participant Ex as executor
  participant DB as donnaschedule
  participant Ar as arbiter
  participant Br as runTurn(proactive)
  participant Save as saveMessages
  participant Del as deliverBurstToUser
  participant CM as chat_messages

  T->>Ex: runScheduleTickOnce()
  Ex->>DB: sweepStuckClaimed(5min)
  Ex->>DB: claimNextPending
(FOR UPDATE SKIP LOCKED)
  alt no row due
    DB-->>Ex: null
    Ex-->>T: return
  else row claimed
    DB-->>Ex: ScheduleRow
    Ex->>Ar: arbitrate({cause, last_assistant_at, now, tz})
    alt arbiter rejects
      Ar-->>Ex: {allow:false, reason, reschedule_at?}
      Ex->>DB: markCancelled(reason)
      opt has reschedule_at
        Ex->>DB: insertSchedule(reschedule_at, same cause)
      end
    else arbiter allows
      Ar-->>Ex: {allow:true}
      Ex->>CM: loadRecentMessages(50)
      Ex->>Br: runTurn({mode, cause, messages})
      Br->>Save: saveMessages(newMessages, "proactive")
      alt terminator: send_burst
        Br-->>Ex: {sends, terminator:"send_burst"}
        loop each burst
          Ex->>Del: deliverBurstToUser(userId, body)
        end
      else terminator: defer
        Br-->>Ex: {terminator:"defer", nextSchedule}
        Ex->>DB: insertSchedule(nextSchedule)
      else terminator: do_nothing
        Br-->>Ex: {terminator:"do_nothing"}
      end
      Ex->>DB: markFired
    end
  end

concurrency & recovery

  • FOR UPDATE SKIP LOCKED — atomic claim across N worker instances. instance A grabs row 1, instance B grabs row 2 (or null), no double-fire.
  • sweepStuckClaimed(thresholdMinutes=5) — rows in status='claimed' for >5min get reset to pending. handles process-crash recovery.
  • in-process _ticking guard prevents overlapping ticks within a single instance.

18. multi-turn agendas — the primitive

donna's working-memory for conversations that span replies. one tiny table, one tool, one composer block. subscriptions onboarding is the first user; future flows (calorie goal-setting, integration mode-walkthrough, anything that asks then waits) reuse the exact same shape.

18.1 state machine

  state active {

    step2 --> step3: agendas_advance

  active --> completed: terminal step reached
  abandoned --> [*]

18.2 mechanism — three pieces

storage
donna_state_agendas(id, user_id, kind, step, payload jsonb, status, created_at, updated_at) — index on (user_id, status, kind) so the composer's "what's open?" query is one b-tree lookup.
composer block
src/donna/composer/agendas.ts exports loadActiveAgendas(userId) and renderAgendasBlock(rows). brain's reactive prompt assembly calls these and prepends an <active_agendas> XML block before <chat_history>.
tool
agendas_advance({id, next_step, payload?, status?}) — direct, reactive only. tiny by design: the prompt teaches donna which step follows which (per kind), the tool just persists.

18.3 prompt contract

the <agenda_handling> block in REACTIVE_SYSTEM_PROMPT lists each kind, the legal step transitions, and the tools to call at each. when donna sees an active agenda in <active_agendas>, she follows that contract instead of inventing flow. when she calls agendas_advance(status="completed"), the row drops out of the block and she's free.

why so small. we resisted building a full state machine library. one row, one tool, one block — the prompt does the orchestration. if a future agenda needs branching, it's a new kind with new steps; the primitive doesn't grow.

POST /composio/webhook on donna-web. fast-acks 200 after signature verify, dispatches asynchronously. invalid signature → 401, no body parse.
cause mapping
buildCause in composio_webhook.ts dispatches by triggerSlug. GMAIL_* → kind: "gmail_event" with extracted {message_id, thread_id, from, subject}. unknown slugs fall back to kind: "scheduled" so the brain still sees them and can decide.
prompt contract
<cause_kinds> block in PROACTIVE_SYSTEM_PROMPT teaches that gmail_event defaults to do_nothing ≥95% of the time. only personal/time-sensitive mail earns a burst — promotions, digests, automated notifications never do.
env
COMPOSIO_WEBHOOK_SECRET (signing secret from composio dashboard) and optional COMPOSIO_GMAIL_TRIGGER_SLUG (defaults to GMAIL_NEW_GMAIL_MESSAGE).
scan_gmail isn't dead, it's narrowed. the recurring inbox-triage cause survives — but its job is now "review the state of the inbox" (stale threads, missed follow-ups), not "discover new mail." new mail is a push lane via gmail_event. one is a sweep, the other is a notification. they don't overlap.

20. gmail intelligence — threads, people, ball-in-court

email isn't a stream of text, it's a graph of obligations. donna's gmail intelligence layer turns inbox messages into two typed stores — gmail_threads (the spine) and gmail_people (the saliency prior) — that downstream tools query directly. you stop opening gmail; you talk to donna.

20.3 the data

gmail_threads domain

one row per gmail thread donna learns about. computed columns drive every downstream query.

fieldmeaning
stateawaiting_user · awaiting_other · scheduled · closed · fyi
ball_in_court'user' · 'other' · null
awaiting_sincewhen the ball started sitting in current court — preserved across same-ball updates
one_line_summary≤120 char human-readable summary written by classifier
importance_score0..1 = base × counterparty salience (clamped). pinned threads floor at 0.85
user_dismissed / user_pinnedexplicit user overrides — survive future updates

gmail_people domain

people-graph derived from threads. one row per counterparty email. saliency_score is the prior the brain uses to filter push events and to interpret "who matters."

fieldmeaning
inbound_count_30d / outbound_count_30dengagement counters
reply_rateoutbound_total / inbound_total — low + high inbound = noise
salience_scoreengagement × reply_rate × recency. recomputed on every event
is_bot_likelynoreply@ / notifications@ / mailgun-style domains — excluded from people_top by default

20.5 push event hot-path

this is where the layer pays for itself. without intelligence, every gmail push wakes the brain, runs an llm, decides "do_nothing" 95% of the time. with the threads layer, the heuristic classifier triages the event in <10ms — bots, low-importance, ball-on-other → silent audit row, no brain wake. only events with ball=user AND importance ≥ 0.55 spend an llm call.

20.6 conversational surface

you saydonna does

"who am i ghosting"people_top() + filter rows where reply_rate < 0.3 + inbound > 5

(silently, monday 9am)scan_gmail wake → threads_open_for_me → only burst if anything > 7 days ball-on-user
(push from stranger)heuristic: bot/low-salience → silenced via audit, brain never woken
(push from boss with question)heuristic: awaiting_user + high importance → cause + summary in payload → brain confirms with threads_get → burst
this is the same shape as subscriptions. source adapter → heuristic+haiku classifier → typed aggregator → tool surface. every future domain (calendar, contacts, commitments) follows the same pattern. the substrate doesn't change.
