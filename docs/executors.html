the executor pattern · current as of 2026-05-24

the executor.

voice brain holds personality. executors hold work. a stateless leaf agent spawned per task, given a goal, returns a structured answer. voice frames it as a user reply. one pattern, applied first to research, generalises to gmail, calendar, drafting — each just a different bundle factory.

1 · the thesis

the voice brain is the user-facing personality. the moment a request needs current external information — search, fetch, scrape, code-driven filtering — voice delegates to an executor. the executor has tools voice doesn't. the executor returns a clean structured answer. voice turns that answer into a burst.

this is the poke pattern, adapted: voice and execution split, with one specific reason — keep the voice brain's context (and its prompt) clean while letting the executor have heavy tool surfaces it needs to do real work.

not three tiers, two. poke runs voice → execution → leaves. donna collapses voice and execution into one tier (the voice brain is itself the dispatcher); executors are the second tier. simpler, fewer hops, sufficient for now.

3 · the dispatch contract

between voice and executor — the exact wire shape.

voice → executor

voice emits a tool_use:

{
  type: "tool_use",
  name: "dispatch_to_executor",
  id:   "toolu_01...",
  input: {
    task: "find current opening hours for blue bottle coffee at 66 mint plaza, san francisco"
  }
}

one field — task. the executor sees only this string, plus its own system prompt. it does not see voice's conversation. it does not know who the user is by name. the task must be self-contained.

executor → voice

the executor's last action is calling finalize_research with structured args:

{
  type: "tool_use",
  name: "finalize_research",
  input: {
    answer:  "blue bottle at 66 mint plaza is open 7am-6pm weekdays, 8am-6pm weekends.",
    sources: ["https://bluebottlecoffee.com/cafes/mint-plaza"]
  }
}

the dispatch handler reads answer and sources directly from the assistant's tool_use input — not from the tool_result. the tool_result is just an ack. the structured args ARE the payload.

handler returns to voice:

{
  answer:  "blue bottle at 66 mint plaza is open 7am-6pm weekdays, 8am-6pm weekends.",
  sources: ["..."],
  runId:   "a1b2c3d4-..."
}

which voice sees as a tool_result block:

{
  type: "tool_result",
  tool_use_id: "toolu_01...",
  content: "{\"answer\":\"blue bottle at...\",\"sources\":[...],\"runId\":\"...\"}"
}

voice's next iteration sees the answer, decides what to say to the user, calls send_burst.

why answer lives in tool_use input, not tool_result. the model already structured the answer when it called finalize_research. parsing it out of the tool_use input means we read what claude meant, not a re-encoded round-trip through the tool handler.

nested runTurn. parent loop calls dispatch_to_executor; the dispatch handler invokes runTurn again with a different bundle; everything composes through the same brain primitive.

i voice decides model picks dispatch_to_executor because the answer needs external info it doesn't have. writes a self-contained task.
ii handler builds bundle researchBundle(task) returns a fresh AgentBundle with the task injected into its prompt.
iii executor runs nested runTurn — same loop, different bundle. server tools fire under the hood, anthropic does the heavy lifting.
iv voice frames handler extracts answer + sources, returns as tool_result. voice's next iteration writes the user-facing bubble.

5 · why stateless

each dispatch starts from zero. no per-user executor history is loaded. the transcript exists for one dispatch then is discarded (ledger keeps an audit trail; nothing is loaded back).

the four reasons

  • predictable cost per call. no accumulation. every dispatch has roughly the same token budget. no surprise compounding for heavy users.
  • parallel-safe by default. two dispatches in one voice turn can fire concurrently — they share no state, no locks needed.
  • clean data lifecycle. "delete my account" has fewer surfaces to scrub. executor transcripts don't outlive the dispatch.
  • the voice brain naturally holds cross-dispatch memory. voice's own chat history captures every dispatch_to_executor tool_use and its returned answer as a tool_use / tool_result pair. when the user asks "what was that you found earlier", voice already has it.

what we lose

  • no cross-dispatch learning inside the executor. if dispatch 1 figured out which blue bottle is the right one, dispatch 2 doesn't know — unless voice puts it in the task field.
  • multi-turn refinement inside the executor ("now sort by price") requires voice to re-dispatch with prior findings included.
  • partial-failure recovery is poor — a crashed mid-task starts over from scratch.

when this stops being the right call

three conditions, watching for any of them:

  • real cross-dispatch continuity demand. if "follow up on what we discussed yesterday" becomes a high-frequency pattern, the voice-tier integration cost gets uncomfortable.
  • long-running per-domain workflows. a gmail flow that spans hours/days (chase, follow up, escalate) outgrows the leaf shape.
  • cross-domain coordination. "schedule with whoever emailed about X" needs a middle tier that holds the in-flight task across multiple sub-domains.

when any of those land, the pattern evolves toward poke's middle tier: stateful per-domain execution agents that load per-user history before working. for now: leaves.

6 · the four files

filewhat it owns
src/donna/agents/research.tsresearchBundle(task) — factory that returns a fresh AgentBundle per task.
src/donna/tools/finalize_research.tsthe executor's terminator. takes { answer, sources? }.
src/donna/tools/dispatch_to_executor.tsthe voice-side bridge. handler invokes runTurn with the research bundle and extracts the structured answer.
src/donna/tools/index.tsregisters dispatch_to_executor in voice's tool catalog (not a terminator).

nothing in brain.ts changed. the loop is role-agnostic — it ran for voice already, it runs for the executor without any modification.

// research.ts (sketch)
export function researchBundle(task: string): AgentBundle {
  return {
    name: "donna.research",
    systemPrompt: `${RESEARCH_PROMPT}\n\ntask:\n${task}`,
    tools: [
      { type: "web_search_20260209", name: "web_search", max_uses: 5 },
      { type: "web_fetch_20260209", name: "web_fetch", max_uses: 5 },
      { type: "code_execution_20250825", name: "code_execution" },
      finalizeResearchTool,
    ],
    handlers: { finalize_research: finalizeResearchHandler },
    terminators: new Set(["finalize_research"]),
  };
}

7 · the research executor — tools

toolkindrole
web_search_20260209 server tool (anthropic) open-web search. dynamic filtering on opus 4.6+ / sonnet 4.6+. citations come back automatically.
web_fetch_20260209 server tool (anthropic) fetch a specific url. used when search results don't have the depth needed.
code_execution_20250825 server tool (anthropic) python + bash sandbox. used for filtering, parsing, structured post-processing. free when bundled with web_search or web_fetch.
finalize_research custom (our code) terminator. takes structured answer + sources. handler is a minimal ack — the answer lives in the tool_use input.
server tools mean less of our code runs. when the executor calls web_search, anthropic does the fetch on their side and hands the result back in the same response. no round trip through our handler. our infrastructure burden = exactly the cost of running runTurn one extra time, no more.

why finalize_research isn't send_burst

send_burst emits user-facing bubbles. the executor never talks to the user. it returns a structured answer for the parent (voice) to frame.

keeping finalize_research as a separate terminator means:

  • the executor's prompt explicitly says "you are not user-facing" — the model is trained on the shape of its output.
  • voice owns all personality. swap voice's prompt, every executor's output gets rewritten in the new voice automatically.
  • adding more executors doesn't multiply user-voice surfaces. each one has its own finalize tool; only voice has send_burst.

8 · parallel dispatch

since the executor is stateless, two dispatches can run in parallel from one voice turn. anthropic's models default to parallel tool emission when calls are independent.

sequenceDiagram
  autonumber
  participant V as voice brain
  participant D as dispatch handler
  participant R1 as research executor #1
  participant R2 as research executor #2

  V-->>D: tool_use: dispatch_to_executor({task: "weather seattle"})
  V-->>D: tool_use: dispatch_to_executor({task: "stock price aapl"})
  Note over D: handler runs both in parallel
  par
    D->>R1: runTurn(weather task, researchBundle)
    R1-->>D: { answer: "55°F, drizzle" }
  and
    D->>R2: runTurn(stock task, researchBundle)
    R2-->>D: { answer: "$185.42" }
  end
  D-->>V: tool_result × 2
  V-->>V: send_burst (combines both into one reply)

two independent lookups → one voice turn → one combined reply. nothing in the architecture serialises them.

donna's voice prompt has an explicit "efficiency" stanza nudging this:

// from prompt.ts
efficiency:
- when you need multiple independent pieces of info, request them in
  one turn — emit multiple tool calls in the same response. chain only
  when one depends on another's result.

9 · what's next

thingstateshape
research executor live shipped. web_search + web_fetch + code_execution + finalize_research.
gmail executor later different bundle factory. tools: gmail_search, gmail_read_thread, gmail_draft, finalize_gmail. server-side via composio.
calendar executor later tools: calendar_list, calendar_create_event, finalize_calendar.
drafting executor later composes long-form text (replies, summaries). returns a draft id and preview.
parametric tool subsetting later option B from the design — bundle picks its tool subset at dispatch time from a global registry. only needed if executor types start to multiply.
stateful per-domain executors later option B/poke pattern. only ship if leaf-style stops fitting product needs.
memory tool later orthogonal to executors. unified per-user memory store. once executors and voice both write to it, executors don't need to be stateful themselves.

the dispatch_to_executor will eventually grow a type arg

when the second executor lands, the tool becomes:

dispatch_to_executor({
  type: "research" | "gmail" | "calendar",
  task: string,
})

handler switches on type, calls the right factory. nothing else changes. the parametric pattern (researchBundle, gmailBundle, calendarBundle as factories) is already the right shape — we just add more.
