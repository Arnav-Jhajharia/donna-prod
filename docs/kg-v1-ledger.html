option 1 of 3

ledger-first. typed entries are the unit.

events are an audit log. the model and tools read from a typed day-entries table — every meeting, commitment, mood note, and donna-action is a row with a kind. fast queries, natural tools, schema you can index.

1. thesis

the day is a stream of typed things. each thing is a row with a kind. donna reads, queries, and reasons over these rows. raw events still exist as a truth log, but they're not the primary read path — they're for replay and audit.

tradeoff up front: you trade replay purity (option 2) and unified-stream simplicity (option 3) for tool ergonomics. when the model asks "what commitments does the user have open this week," you're one indexed query away, not a derivation pipeline away.

2. schema

tables

tablecardinalitywhat it is
events~100-300/day/userappend-only audit log. everything donna sees or does.
day_entries~50-150/day/usertyped rows. the model's primary read surface.
day_narrative1/day/usersealed at end-of-day. vibe summary + open threads.
entities~hundreds/userpeople, places, projects, recurring things.
edges~thousands/usertyped relations between entities.
rhythms~tens/userderived patterns. "gym tue/thu 7am, p=0.85".

day_entries — the central table

{
  id           uuid pk,
  user_id      uuid not null,
  date         date not null,          -- user's local date
  ts           timestamptz not null,   -- exact moment
  kind         entry_kind not null,    -- enum, see below
  payload      jsonb not null,         -- shape varies by kind
  entity_refs  uuid[] not null default '{}',
  source_event_ids uuid[] not null,    -- provenance
  created_at   timestamptz default now()
}

-- indexes
(user_id, date)
(user_id, kind, date)
(user_id, entity_refs gin)

entry kinds

  • meeting from cal, or mentioned in chat. payload: title, with[], duration, notes.
  • commitment "i'll call mom tonight". payload: what, due, status.
  • mood_note inferred or stated. payload: signal, evidence.
  • donna_notification donna sent something proactively. payload: text, channel, trigger.
  • donna_reminder a reminder donna fired. payload: text, original_commitment_id.
  • mention a person/place/project came up. payload: entity_id, context.
  • observation something donna noticed. payload: what, evidence.
  • integration_signal non-message integration delta worth keeping. payload: source, what.
  • thread_opened / thread_closed conversational thread state changes.

day_narrative

{
  user_id      uuid not null,
  date         date not null,
  sealed       bool default false,
  summary      text,           -- 3-6 sentences
  open_threads text,           -- what's hanging
  energy       text,           -- 'flat' | 'sharp' | 'low' | ...
  generated_at timestamptz,
  primary key (user_id, date)
}

3. write path

flowchart LR
  IN[message / integration / donna action] --> EV[(events)]
  EV --> EX[extractor]
  EX -->|typed rows| DE[(day_entries)]
  EX -->|nodes/edges| GR[(entities + edges)]
  EX -->|live update| NA[(day_narrative
unsealed)]
  CRON[nightly worker] -->|seal| NA
  CRON -->|recompute| RH[(rhythms)]
  1. every inbound (message, integration delta) and every outbound (donna action) writes one event.
  2. extractor runs per event. emits zero or more day_entries, updates entities/edges, may update unsealed narrative live.
  3. at user's local midnight: seal the narrative, refresh rhythms across recent days.

4. read path

the model gets a context bundle per turn. tools provide on-demand access.

standard per-turn bundle

// pseudocode
context = {
  today:      query day_entries WHERE user=X AND date=today ORDER BY ts,
  narrative:  query day_narrative WHERE user=X AND date IN last_7,
  graph_1hop: for entity in mentioned_entities: get node + edges,
  rhythms:    query rhythms WHERE user=X AND dow=today_dow,
  pending:    query day_entries WHERE user=X AND kind='commitment' AND status='open',
}

tools the model can call

toolreturns
get_day(date)all entries + narrative for one day

get_entity(name_or_id)node + 1-hop neighborhood

5. worked example — the 5pm dentist nudge

walking one moment through the system end-to-end.

sequenceDiagram
  participant U as user
  participant D as donna
  participant E as events
  participant DE as day_entries
  participant G as graph

  Note over D,G: yesterday — user mentions dentist
  U->>D: "remind me to book the dentist tomorrow"
  D->>E: event(kind=message_in)
  D->>DE: entry(kind=commitment, due=tomorrow 5pm)
  D->>G: edge(user, has_appointment_with, dentist)

  Note over D,G: today 5pm — scheduler fires
  D->>E: event(kind=donna_outbound, trigger=commitment#42)
  D->>U: "did you book the dentist?"
  D->>DE: entry(kind=donna_reminder, ref=commitment#42)

  Note over D,G: user replies
  U->>D: "yeah, booked for next tuesday"
  D->>E: event(kind=message_in)
  D->>DE: entry(kind=meeting, title=dentist, when=next_tue)
  D->>DE: update commitment#42 status='done'

three weeks later when the user says "didn't you remind me about something on the 21st?" donna can answer because day_entries WHERE date='2026-05-21' AND kind='donna_reminder' returns the row instantly.

6. rhythms — "what's usual this day"

nightly job aggregates last 60 days of entries per user. groups by day-of-week and entry-kind. detects recurrences with enough density to call them patterns.

rhythms row:
{
  user_id, dow: 'tue', kind: 'meeting',
  signature: 'gym',         -- normalized
  typical_time: '07:00',
  confidence: 0.85,
  last_observed: '2026-05-13'
}

per-turn, donna can pull rhythms for today's dow and notice the absence: "user didn't mention gym today, that's unusual for tuesday."

7. tradeoffs

good at

  • tool ergonomics — query maps to intent
  • indexable, fast for "what's open / what happened today"
  • typed rows = the model gets clean, predictable shapes
  • donna's own actions are first-class entries, not buried in events

costs

  • two write paths (events + entries) — possible drift
  • extractor logic gets sprawling as kinds proliferate
  • schema migrations when a new kind needs new payload shape
  • cross-table joins for some questions

8. when to pick this

pick this if shipping fast matters and the model needs clean, queryable shapes. it is the most pragmatic of the three — the one that gets donna useful in v0.4 even if it costs some replay purity.

opt 2 trades this for stricter purity. opt 3 trades it for a simpler mental model.
