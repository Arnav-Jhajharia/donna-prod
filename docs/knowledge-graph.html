1. thesis

the only invariant donna keeps is the event log. everything she "knows" — the graph, today's vibe, this week's threads — is a projection of that log, regenerable from scratch.

why this matters: personal AI fails when its understanding silently drifts from reality. an event-sourced foundation gives us two non-negotiables: provenance (every belief traces back to an event) and recovery (when extraction logic gets smarter, old data gets smarter too).

the rule, stated once

  • immutable   events — append-only. corrections are new events, not mutations.
  • derived   daily snapshots — persisted, but rebuildable.
  • mutable   graph — working representation. mutate freely. if it gets wrong, nuke and replay.

2. the three layers

each layer compresses the layer below it. events are high-fidelity and high-volume. snapshots compress a day. the graph compresses across time.

3. events — the only truth

everything donna ever sees gets written as an event before anything else happens. extractions, snapshots, graph updates — all downstream of this write.

shape

{
  id:         uuid,
  ts:         iso8601,            // when it happened
  ingested_at: iso8601,           // when donna saw it
  source:     'whatsapp' | 'imessage' | 'gmail' | 'cal' | 'donna' | ...,
  actor:      'user' | 'donna' | 'system' | external_id,
  kind:       'message' | 'fact_asserted' | 'fact_corrected' |
              'integration_event' | 'tool_call' | 'observation' | ...,
  payload:    jsonb,              // shape depends on kind
  supersedes: uuid?               // if this event corrects/replaces an earlier one
}

what counts as an event

  • every inbound and outbound message
  • every integration delta (new gmail thread, calendar change, etc)
  • every fact donna asserts about the user ("user mentioned they're moving to NYC")
  • every correction ("actually it's seattle, not NYC")
  • every tool call donna makes — observable, audit-able

what does not get logged here

  • model thoughts / chain-of-thought
  • intermediate prompt construction
  • cache state, retrieval scores
  • anything that's pure compute over events

corrections via supersedes

the log is never edited. when a prior fact turns out wrong, you append a new event that points at the one it replaces. the graph reads "latest non-superseded fact." the history stays intact, so you can always answer "when did donna start believing this."

provenance: every edge in the graph carries the event id(s) it came from. "why does donna think i live in SF?" → trace to event → see the message that said it. trust is built on traceability.

4. daily snapshots

one row per day. structured fields the agent can query directly, plus a narrative the model can read. sealed at end of day, but updated continuously until then.

shape

{
  date:           '2026-05-20',
  sealed:         boolean,

  // structured — queryable
  meetings:       [{ time, title, with[], notes? }],
  commitments:    [{ what, to_whom?, due?, status }],
  people_seen:    [string],
  topics:         [string],
  integrations:   { gmail_threads, cal_changes, ... },
  mood_signals:   ['flat', 'energized', 'anxious', ...],

  // narrative — for the model
  summary:        text,   // 3-6 sentences. what the day felt like.
  open_threads:   text,   // what's hanging, what to revisit

  // links back
  source_event_ids: uuid[]
}

the seal job

at the user's local midnight (or first message after), the day's events get rolled up. structured fields populated by deterministic extractors. narrative fields generated by the model with the day's events as context. then the row is marked sealed.

sealed rows are still regenerable — if the rollup logic improves, you can re-seal historical days from events. but in normal operation, sealed = read-only.

why snapshots are the unlock

the graph tells you sarah is your sister. the snapshot tells you you called sarah tuesday and she sounded off. together that's the kind of context a sharp chief of staff brings. neither alone is enough.

snapshots are also what you hand to the model when the user asks "what was last week like" — without dumping ten thousand tokens of raw chat.

5. the graph

entities and edges. mutable. no temporal validity baked in — the events already have that, and the graph can be rebuilt at any time. keep the schema simple and let it evolve.

what's in it

entities
people, places, projects, organizations, recurring things (gym, therapy, the dog), preferences, habits, beliefs the user holds.
edges
typed relations between entities. (user, dating, sarah). (user, works_at, anthropic). (sarah, lives_in, brooklyn). (user, dislikes, surprises).
provenance
each edge keeps the event id(s) it was derived from. cheap audit trail.
confidence
a single float. extractions are not certain. low-confidence edges get verified before use.

resolution at write time

the hardest part of running a personal graph isn't storage — it's making sure "sarah" and "sarah k" and "@sarah_k" and "my sister" point at the same node. resolve at ingest, not at query. a fragmented graph silently corrupts every answer downstream.

decay, gently

facts go stale silently. "sarah works at stripe" was true a year ago. two defenses:

  • confidence decay over time — older edges with no reinforcement lose confidence. donna hedges before asserting.
  • periodic reconfirmation — high-stakes edges (relationships, employers, addresses) get gently re-checked in conversation when stale.

6. replay as a superpower

because the graph and snapshots are pure functions of the event log, you can throw them away and rebuild. this is not a recovery feature — it is the central design unlock.

what it buys

  • smarter past. when extraction prompts get better, re-run them over old events. yesterday's data gets smarter without re-collecting.
  • debuggability. "why does donna think X" → find the event, read it. no black box.
  • schema freedom. the graph schema can change in any release. snapshots can take new fields. the log doesn't care.
  • trust recovery. if the graph gets corrupted by a bad extraction pass, drop the table and replay. nothing is lost.
the price: extraction must be a pure function over events. no hidden state. no "this only works if you process events in order with the previous graph loaded." pure in, pure out. that discipline is what makes replay safe.

7. how the brain reads

per turn, the brain assembles context by pulling from all three layers in a specific pattern. the goal is enough signal to act like a sharp chief of staff — not a token-dump.

retrieval pattern, per turn

  1. today's snapshot — full. this is what's live. always loaded.
  2. recent snapshot summaries — last 7 days, narrative field only. ambient context without bloat.
  3. graph: 1-hop from mentioned entities — if the message mentions sarah, pull sarah's node + edges. don't pull the whole graph.
  4. recent raw events — last 24h, in order. the model needs to see actual phrasing, not just compressed structure.
  5. on-demand graph queries — exposed as a tool. the model can ask "what do i know about X" when context isn't enough.
retrieval, not storage, is the unsexy bottleneck. a perfect graph the brain never queries is dead weight. the design only pays off when context assembly is sharp.

8. the actually hard problems

storage is easy. these are not.

problemwhy it's hardwhere it lives
entity resolution "sarah" / "sarah k" / "@sarah_k" / "my sister". get this wrong at ingest and the graph fragments. extraction pipeline
fact decay silent staleness. donna confidently says something true 18 months ago. graph + retrieval
extraction discipline pure functions over events. no hidden state. or replay breaks. extractors
context bloat easy to dump everything into the prompt. expensive and worse, not better. retrieval / context assembly
seal correctness the daily rollup runs once. if it gets the day wrong, downstream feels it for weeks. snapshot worker
cost of writes every inbound triggers extraction. needs to be cheap or batched smartly. write path

9. build order

line-by-line, in this order. nothing built ahead of when it pays off.

  1. event schema + write path. every inbound and outbound goes through it. nothing else exists yet — events alone are useful as an audit log.
  2. extraction over events. a single pass that pulls entities + relations from each event. write to a flat extractions table first; graph shape comes later.
  3. entity resolution. the moment you have two events naming the same person, this matters. invest here early.
  4. graph from extractions. derive nodes + edges. keep schema simple. start mutable, no temporal fields.
  5. daily snapshot worker. end-of-day rollup. structured first, narrative second.
  6. retrieval in brain.ts. wire context assembly. measure what the model actually uses.
  7. confidence + decay. only once the graph has been live long enough that staleness shows up in the product.
  8. replay tooling. a script that rebuilds graph + snapshots from events. cheap insurance.

the goal is not a clever graph. the goal is a foundation that lets donna grow sharper over time without ever losing what she's seen. the event log is the promise. everything else serves it.
