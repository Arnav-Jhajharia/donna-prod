1 · the one call

the entire sdk is a thin wrapper around one http endpoint: POST /v1/messages. everything you'll read below — caching, streaming, thinking, vision, tools, batches — is a different way of shaping that single call.

install, instantiate, send:

// npm i @anthropic-ai/sdk
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();  // reads ANTHROPIC_API_KEY from env

const response = await client.messages.create({
  model:      "claude-sonnet-4-6",
  max_tokens: 1024,
  system:     "you are donna.",
  messages:   [{ role: "user", content: "hey" }],
});

console.log(response.content);

that's the whole api surface in five lines. everything else is parameters on that one call, plus three siblings: messages.stream (sse), messages.countTokens (estimate), and messages.batches.create (async).

auth. new Anthropic() with no args reads ANTHROPIC_API_KEY from the environment. donna sets it in .env. nothing else is required to talk to the api.
concurrency. every entry point is async. await client.messages.create() pauses your function, not the node event loop — two users hitting the webhook at the same time both have their requests flying to anthropic in parallel. node is single-threaded but i/o is non-blocking, so hundreds of in-flight calls cost ~zero cpu while they wait. what you actually have to guard against is per-workspace rate limits (the sdk retries 429s for you) and per-user turn serialisation (one user's turn n+1 should start after turn n's history persists — that's a queue per user, not a property of messages.create).

the four entry points

messages.create
one-shot. returns a promise that resolves when the full response is back. async — the node event loop keeps running, so other turns can fly in parallel. what donna calls today in brain.ts.
messages.stream
same payload, server-sent events. emits deltas as the model writes. needed the moment we wire voice or want typing-indicator pacing.
messages.countTokens
cheap pre-flight: how many input tokens does this payload weigh. no completion, no cost on output. useful for context budgeting.
messages.batches.create
fire-and-forget. up to 100k requests, 24h sla, ~50% off list. the right shape for the proactive worker and overnight reflection.

2 · the request, byte by byte

a MessageCreateParams is a small, fixed shape. every field below is either present on every request donna makes, or earns its place in a specific section later.

{
  model:        string,                // "claude-sonnet-4-6", "claude-opus-4-7", "claude-haiku-4-5-20251001"
  max_tokens:   number,                // hard cap on the completion. required.
  system:       string | Block[],      // the standing instructions
  messages:     MessageParam[],        // the conversation, oldest first

  tools?:       Tool[],                // what the model is allowed to call
  tool_choice?: { type, ... },         // force / forbid / suggest a tool

  temperature?: number,                // 0..1. lower = more deterministic. default 1. forced to 1 with thinking.
  stop_sequences?: string[],

  thinking?:    { type, budget_tokens }, // extended thinking
  stream?:      boolean,                 // implied by messages.stream()

  metadata?:    { user_id },           // abuse signal, not analytics

  context_management?: { ... },        // auto-compaction directives
  betas?:       string[],              // opt-in to new features pre-ga
}

three things to know now and forget the rest until you need them:

  • max_tokens is required and is the output ceiling. the model will be cut off mid-token if it reaches the cap. set it generously.
  • system sits outside messages. you don't repeat it. you don't put it in role "system" — there's no such role.
  • messages must alternate user → assistant → user → … starting with user. tool results live inside a user message as tool_result blocks.
  • no top_p / top_k. the messages api dropped them. temperature is the only sampling knob, and it's clamped to 1 when extended thinking is on.

3 · the response, block by block

a Message comes back like this:

{
  id:           "msg_01...",
  type:         "message",
  role:         "assistant",
  model:        "claude-sonnet-4-6",
  stop_reason:  "end_turn" | "max_tokens" | "stop_sequence" | "tool_use" | "pause_turn" | "refusal",
  stop_sequence: string | null,
  content: [
    { type: "thinking",           thinking: "...",  signature: "..." },
    { type: "text",               text: "hey, what's up", citations?: [...] },
    { type: "tool_use",           id: "toolu_01...", name: "get_current_time", input: {...} },
    { type: "server_tool_use",    ... },           // code_execution, web_search
    { type: "web_search_tool_result", ... },
  ],
  usage: {
    input_tokens:                number,
    output_tokens:               number,
    cache_creation_input_tokens: number,   // what we paid the +25% premium on
    cache_read_input_tokens:     number,   // what we read at 10%
  }
}

content is an array, always

the model can emit any number of blocks in any order. a single response may contain a thinking block, then a text block of private reasoning, then three tool_use blocks. you handle each by its type.

filter assistant text alongside tool_use. when the model emits text in the same turn as a tool call, that text is private scratch — not for the user. donna's filterAssistantContent in brain.ts drops it before persisting so it can't poison future turns. keep thinking and redacted_thinking blocks though — the api requires them to round-trip.

stop_reason — what just happened

stop_reasonmeaningdonna does
end_turnmodel decided it was done.shouldn't happen mid-loop — every turn must end with send_burst. log + bail.
tool_uselast block is a tool call. needs to be run and its result fed back.the happy path. dispatch, append result, iterate.
max_tokensoutput ceiling tripped. truncated mid-block.bump max_tokens or split the work. tool_use cut off mid-json is unrecoverable.
pause_turnlong-running server tool (web_search, code_execution) needs another lap.send the message right back, unchanged, to continue.
stop_sequencehit one of your stop_sequences.rare. n/a for donna today.
refusalmodel declined. assistant content explains.surface in a burst, never silently swallow.

4 · picking the model

three families, three speeds. the model id is a string. swap it and the request shape doesn't change.

claude-opus-4-7

opus

the smart one. best for planning, multi-step reasoning, tricky tool orchestration, code. supports a 1M-token context window. slower and ~5× the price of sonnet.

for donna: the overnight reflection pass. the executor planning a multi-day project. anything where being right matters more than being fast.

claude-sonnet-4-6

sonnet

the workhorse. very close to opus on most tasks, ~3× faster, much cheaper. the default for chat-shaped workloads.

for donna: the voice loop. every text turn she takes is this model. DEFAULT_MODEL in brain.ts.

claude-haiku-4-5-20251001

haiku

the fast one. low latency, low cost, smart enough for routing and classification. dated id (pinned snapshot).

for donna: trigger fire-decisions ("is this signal worth waking the brain"), classifier sub-agents, summarising long threads before they enter the brain.

the 1M context window

opus 4.7 with the context-1m-2025-08-07 beta accepts up to a million input tokens. the wrong way to think about this is "now we never compact." the right way is: when you genuinely need a lot in front of the model in one shot — a full inbox, a full journal — pay for it. for normal turns, even a busy week of donna chat is only thousands of tokens. don't pre-optimise for a window we won't fill.

const client = new Anthropic({
  defaultHeaders: { "anthropic-beta": "context-1m-2025-08-07" }
});

model aliases

the api also accepts unsuffixed names like claude-sonnet-4-6 (alias to the current snapshot) and claude-opus-4-7. donna uses these. when reproducibility matters (eval runs, batched overnight jobs we want to replay) pin a dated snapshot id instead.

5 · the system prompt

the system field is everything that's true on every turn. donna's lives in src/donna/prompt.ts and is the source of her voice.

two shapes are accepted: a plain string, or an array of text blocks. the array form is what unlocks caching:

system: [
  { type: "text", text: STATIC_VOICE_RULES, cache_control: { type: "ephemeral" } },
  { type: "text", text: dynamicLivingProfile }            // changes turn to turn
]

donna today sends a single string. when the living profile lands, splitting it into a static-then-dynamic pair with a cache breakpoint between is how we pay the prompt once per session, not once per turn.

per-turn overlay. TurnConfig.systemOverlay in brain.ts appends a string to the agent's standing prompt for one turn only — for mode switches (reactive vs proactive) without rewriting the whole prompt. the overlay is concatenated after the agent prompt, not cached.

6 · messages & history

the conversation is an array of MessageParam: { role, content }. role is user or assistant — there is no system role and no tool role. tool results live inside a user message as tool_result content blocks.

the alternation rule

messages must alternate strictly: user → assistant → user → assistant → …. starting with anything other than user is an error. two consecutive messages of the same role is an error. if you're appending tool results, they go in a single user message after the assistant's tool_use response, even if there are five of them.

content shapes

each message's content can be a string (sugar for one text block) or an array of blocks. the block types donna sees:

blockrolewhat it is
textuser / assistantthe plain words.
imageusera picture the user shared.
documentusera pdf, plain text, or custom content. supports citations.
tool_useassistant"i'd like to call this tool with this input."
tool_resultuser"here's what that tool returned." matched by tool_use_id.
thinking / redacted_thinkingassistantprivate reasoning. must be round-tripped if present.
server_tool_use & resultassistant / usercode_execution, web_search — server runs them, blocks appear in transcript.

history discipline

donna persists messages in chat_messages. four rules, learned the hard way:

  • persist after filter, not before. the filterAssistantContent pass strips leaked text. if you save raw, those leaks come back as conversation next turn and the model imitates its own scratch.
  • tool_use blocks must have matching tool_result blocks in the very next user message. if you bail mid-iteration without writing the result, the conversation is malformed and the next turn will 400.
  • thinking blocks must round-trip. if the model produced a thinking block this turn and we feed history back next turn, that block has to be there with its signature intact, or the api rejects.
  • order matters. messages are oldest-first. the most recent user message is the last item, not the first.

7 · tool use

tools are how the model acts. she can only describe what she'd like — declare the menu, watch her pick, run it, hand her the result.

declaring a tool

{
  name:        "get_current_time",
  description: "wall-clock time. use when reasoning depends on now.",
  input_schema: {
    type: "object",
    properties: {
      timezone: { type: "string", description: "iana zone, e.g. America/Los_Angeles" }
    },
    required: []
  }
}

the schema is plain json-schema. the model uses description heavily — write it for the model, not for you. say when to call it, not just what it does.

the loop

donna's loop, in five steps, all in brain.ts:

ibuildPayloadsystem + tools + history + cache markers
iimessages.createthe one network call
iiifilterAssistantdrop leaked text alongside tool_use
ivdispatchrun handlers, build tool_result blocks
vterminator?yes → return. no → loop.

  U->>B: "what time is it in tokyo"

tool_choice — forcing the model's hand

shapebehaviorwhen donna wants it
{ type: "auto" }default. model decides.every normal turn.
{ type: "any" }must call some tool. cannot reply with plain text.good guardrail when "every turn ends with send_burst" is non-negotiable.
{ type: "tool", name }must call this specific tool.specialist sub-agents — "you are the gmail summariser, your only output is finalize".
{ type: "none" }cannot call any tool.pure text generation modes. not a fit for donna today.

parallel tool calls

by default the model may emit multiple tool_use blocks in one response. donna runs them sequentially in dispatchToolCalls — fan-out parallelism belongs inside a dedicated sandbox tool, not the dispatch layer. set disable_parallel_tool_use: true inside tool_choice if a flow needs one at a time.

errors

when a handler throws, donna turns the throw into a tool_result with is_error: true. the model sees the failure and can adapt next iteration. don't surface errors to the user directly — let the model decide whether to retry, fall back, or admit defeat.

{
  type: "tool_result",
  tool_use_id: tu.id,
  content: "gmail api: 429 rate limited, retry in 60s",
  is_error: true
}

terminators

donna's loop concept, not anthropic's. a terminator is a tool whose call ends the turn. send_burst is the only one today. the handler still runs (so the conversation is well-formed for next turn) and then runTurn returns. see brain.ts:243.

8 · prompt caching

the single biggest lever in the api. mark a point in the request, anthropic caches every byte up to it for ~5 minutes (or ~1 hour with a flag). first request pays a +25% write premium on those tokens. every subsequent request reads them back at 10% of input price.

how it works

you attach cache_control: { type: "ephemeral" } to any cacheable block — a text block in system, a tool definition, an early text in messages. anthropic walks the request from the start and hashes a key that includes everything before that marker. if the key exists in cache, the prefix is read; if not, it's written.

the rules

  • up to four breakpoints per request. anthropic walks from the last back to the first looking for a hit, so you can layer them.
  • cached prefix must clear a model-specific floor or it silently won't cache: opus 4.7 / haiku 4.5: 4096 tokens; sonnet 4.6: 1024 tokens. shorter prefixes return zero in cache_creation_input_tokens — that's how you know it didn't take.
  • two ttls: "5m" (default) at +25% write premium, "1h" at +100% (2×). reads are 0.1× input price either way. specify with cache_control: { type: "ephemeral", ttl: "1h" }.
  • mixing ttls in one request is allowed, but 1h breakpoints must appear before 5m breakpoints.
  • the cached prefix must be byte-identical. one character drift and you wrote a new cache.
  • only the prefix is cached. anything after the last breakpoint is fresh every time.
  • caches are workspace-scoped on the claude api (since feb 2026). org-level isolation on bedrock / vertex.

two ways to mark

manual: attach cache_control: { type: "ephemeral" } to specific blocks. this is what donna does — the last tool definition carries the marker.

automatic: pass cache_control: { type: "ephemeral" } at the top level of messages.create. anthropic places the breakpoint on the last cacheable block for you and moves it forward as the conversation grows. costs one of the four slots. useful for chat-shaped workloads where the right spot to mark drifts each turn.

pre-warming

send a request with max_tokens: 0 to load a prompt into cache without generating any completion. you pay only the write premium on the cached tokens; the response is empty with stop_reason: "max_tokens". useful before a known burst of traffic — for donna, the first turn of a session pays the cache-write fee whether we want it to or not, so pre-warming buys nothing today.

donna today

in brain.ts:buildPayload we mark the last tool definition with cache_control: ephemeral. the breakpoint sits after all tool definitions, so anthropic caches the system prompt plus every tool. iteration 0 of a turn pays the +25% on those tokens, iterations 1-9 of the same turn — and every turn within ~5 minutes — read them back at 10%.

// brain.ts
const tools = [
  ...agent.tools.slice(0, -1),
  { ...agent.tools.at(-1)!, cache_control: { type: "ephemeral" } }
];

we deliberately don't cache messages: it grows each iteration, so the breakpoint would move and the +25% write would never amortise.

where to add breakpoints next

candidateshapepayoff
system promptsplit into [static_voice, dynamic_living_profile], mark the first with cache_control.identical static text across users; high hit rate.
living profileonce it stabilises, treat as static-per-day. cache for the 1h ttl.frequent reads, infrequent writes — the textbook caching shape.
conversation historymark the last user message in long threads. only viable when history isn't being mutated.1m-context turns: the prompt fee gets unbearable without this.
reading hit rate. the response's usage exposes cache_creation_input_tokens (paid 1.25×) and cache_read_input_tokens (paid 0.1×). divide reads by total input tokens to see hit rate. langsmith surfaces this per call.

9 · streaming

same payload, different transport. instead of waiting for the whole response, you get server-sent events as the model writes. one call:

const stream = client.messages.stream({
  model: "claude-sonnet-4-6",
  max_tokens: 1024,
  system: "you are donna.",
  messages: [...]
});

for await (const event of stream) {
  if (event.type === "content_block_delta" && event.delta.type === "text_delta") {
    process.stdout.write(event.delta.text);
  }
}

const finalMessage = await stream.finalMessage();

the event types

eventfires when
message_startonce at the top. carries the initial Message stub with model, id, empty content.
content_block_starteach new block opens. index + block stub.
content_block_deltarepeated. text_delta for text, input_json_delta for tool_use args streaming as partial json, thinking_delta for thinking.
content_block_stopblock closes.
message_deltastop_reason and final usage.
message_stopthe end.

when donna needs streaming

  • voice. tts wants tokens as fast as possible. the moment a sentence boundary is in the buffer, send it downstream.
  • typing indicator. if she's writing a long burst, mobile/whatsapp can show "donna is typing…" until the first delta lands.
  • cancellable thinking. user changes their mind mid-stream — abort the request without paying for completion you discard.

for the cli loop today, non-streaming is the right call. streaming complicates tool dispatch (you'd need to wait for content_block_stop on a tool_use anyway). add it when the surface demands it, not before.

10 · extended thinking

set thinking: { type: "enabled", budget_tokens: 4096 } and the model is allowed to spend up to that many tokens on private reasoning before writing the user-visible response. the reasoning comes back as thinking content blocks (with cryptographic signatures) interleaved with normal text and tool_use.

the rules

  • budget_tokens must be at least 1024, and strictly less than max_tokens.
  • thinking blocks carry a signature field. when feeding history back you must include the block with its signature unchanged, or the api errors.
  • temperature is forced to 1 when thinking is enabled. don't try to set it.
  • with the interleaved-thinking-2025-05-14 beta, thinking blocks may appear between tool_use calls within one response — useful for multi-step reasoning that needs intermediate tool checks.
  • thinking tokens are billed as output tokens. budget accordingly.

when to enable

not by default. donna's chat-shaped turns don't need it. reach for thinking when:

  • the executor is planning a multi-day flow with branching depends-on-result logic
  • the overnight reflection pass is synthesising the day — "what changed, what to surface tomorrow"
  • a sub-agent has to choose between many specialists and needs to weigh tradeoffs

11 · vision

image blocks go in user messages. two sources, same shape on the wire:

{
  type: "image",
  source: {
    type: "url",
    url:  "https://example.com/receipt.jpg"
  }
}

// or base64:
{
  type: "image",
  source: {
    type: "base64",
    media_type: "image/jpeg",         // jpeg, png, gif, webp
    data: "<base64 string>"
  }
}

donna cases

  • "here's the menu, what should i get" — photo from imessage / whatsapp
  • "log this receipt" — expense capture
  • "check this screenshot of the calendar invite" — context capture

multiple images per message is fine — pass several blocks. anthropic resizes anything over the limits transparently. the model's image-token cost is computed from the resized dimensions; rough rule of thumb is ~1.6k tokens per image at typical phone sizes.

12 · documents & files

two flavours: pdfs inline, and the files api for reuse.

inline pdf

{
  type: "document",
  source: {
    type: "base64",
    media_type: "application/pdf",
    data: "<base64 pdf>"
  },
  title: "Q4 statement",                   // optional, helps citations
  context: "bank statement from chase",    // optional, helps the model
  citations: { enabled: true }                // see next section
}

plain text document

{
  type: "document",
  source: { type: "text", media_type: "text/plain", data: "..." },
  citations: { enabled: true }
}

the files api

upload once, reference by id forever. the right shape any time donna sees the same file more than once: a journal pdf, a recurring statement, a long thread export, a dataset the code-execution sandbox will chew on.

still beta. every files-api call needs the header:

anthropic-beta: files-api-2025-04-14

or in the typescript sdk, the same header is added automatically when you call client.beta.files.* and pass betas: ["files-api-2025-04-14"] on any messages request that references a file_id.

upload

import { toFile } from "@anthropic-ai/sdk";

const uploaded = await client.beta.files.upload({
  file: await toFile(
    fs.createReadStream("./journal.pdf"),
    undefined,
    { type: "application/pdf" }
  ),
});

what shape each filetype gets

plain texttext/plaindocumentlarge text dumps where you want citations.

the rest of the surface

list
await client.beta.files.list() — paginated listing of every file in the workspace.
retrieveMetadata
await client.beta.files.retrieveMetadata(file_id) — just the metadata, not the bytes.
delete
await client.beta.files.delete(file_id) — gone. cannot be recovered. may still appear briefly in in-flight requests that already had the id.
download
await client.beta.files.download(file_id) — only for files the model created (skills output, code_execution charts/csvs). you cannot download anything you uploaded.

limits and pricing

  • 500 mb per file, 500 gb per organization total.
  • ~100 rpm on file ops during beta. ask for more if you need it.
  • file operations themselves are free: upload, download, list, delete, metadata.
  • you pay normal input-token rates when content is loaded into a messages call.
  • files are workspace-scoped: every api key in the same workspace can see the same files. persist until deleted.
  • files api is not zdr-eligible. if zdr is a hard constraint for any user data, the inline-base64 path is the safer one.

where donna wants this

casewhy files api wins over inline base64
recurring statements / billssame pdf gets referenced over weeks. upload once on first arrival, reference by id every time the user asks "how much did i spend at blue bottle this month".
the long-form journalthe export grows monthly. upload the latest, reference it across many turns, delete the older snapshot.

13 · citations

enable on a document block and the model returns a citations array on each text block it produces, pointing at the chunks of the source it relied on. you get verifiable grounding for free — no extra prompting, no chain-of-cite.

{
  type: "text",
  text: "the charge on the 14th was at blue bottle for $6.50.",
  citations: [
    {
      type: "char_location",
      document_index: 0,
      document_title: "Q4 statement",
      start_char_index: 1240,
      end_char_index: 1290,
      cited_text: "2026-01-14 BLUE BOTTLE COFFEE $6.50"
    }
  ]
}

for donna: when she answers a question grounded in a doc the user shared, the cited spans are how we link back to the original in the dashboard. "here's where i got that." no hallucination story to spin.

14 · server tools

tools anthropic runs for you, server-side, between turns. they appear in the request like normal tools but you don't dispatch them — they're already executed by the time the response lands. relevant ones:

code execution

two versions in the wild:

versioncapabilitymodel support
code_execution_20250825bash + python + file ops. fresh sandbox per turn.every current model, incl. haiku 4.5.
code_execution_20260120adds repl state persistence across turns and programmatic tool calling (the sandbox calls other tools).opus 4.5+ and sonnet 4.5+ only. not haiku.
tools: [
  { type: "code_execution_20260120", name: "code_execution" }
]

gives the model a sandboxed python + bash environment with numpy / pandas / matplotlib / scikit-learn and friends. it writes code, the server runs it, results come back as content blocks. paired with the files api (same beta header), the sandbox reads files we uploaded and emits charts / csvs we can download.

free when bundled. if a request also includes web_search_20260209 or web_fetch_20260209, code_execution tool calls are free — only standard input/output tokens are billed. that turns "search the web, then post-process with code" into the cheapest shape for any data-heavy answer.

donna case: "summarise my spend last quarter from this csv", "plot my sleep against caffeine for the last 30 days", "extract a calorie total from these receipt photos". with 20260120 the same sandbox can persist between turns, so a "now also break it down by week" follow-up doesn't rebuild the dataframe from scratch.

bash (client-side)

bash_20250124. not a server tool despite the name — the model emits { command } and your handler runs the shell. you provision, isolate, allowlist, ulimit, sanitise. anthropic just owns the protocol.

tools: [
  { type: "bash_20250124", name: "bash" }   // schema-less, the model knows the shape
]

// model emits one of:
{ command: "ls -la *.py" }
{ restart: true }                          // reset the session

pricing: +245 input tokens per call for the tool definition, plus normal token cost on whatever stdout/stderr you return. session state is your responsibility — keep a long-lived bash subprocess per agent thread, or spin one up per turn.

most bash-shaped urges are actually code_execution-shaped. code_execution_20250825 already contains bash + python in an anthropic-hosted sandbox. when the question is "she needs to run a thing," that sandbox is almost always the right answer — anthropic owns the container, files api plugs in, no security on us. reach for the real bash tool only when you genuinely need our env vars, our network, or a file on our disk to persist between turns.

where donna might want it

  • media pipelines. ffmpeg on inbound voice memos before whisper, imagemagick resize on receipts before vision. but build these as named tools (transcribe_audio, normalise_image), not a general shell. the verb being explicit is the whole product.
  • the executor sub-agent. if donna ever has an agent that runs ops — restart a worker, run a migration, kick a cron — bash is the primitive. developer-facing surface, not the user-facing donna.

text editor (client-side)

text_editor_20250728 and text_editor_20241022. sibling of bash: claude emits commands like view, create, str_replace, insert on file paths and your handler executes them. the memory tool reuses this exact protocol, scoped to /memories. for donna outside the memory case, no current need.

computer use

not a server tool — a regular client-side tool with three commands (screenshot, mouse, keyboard) that lets the model drive a desktop. you supply the desktop. typically that's a docker container running a virtual display (xvfb + the anthropic reference image) that you ssh / vnc into.

not on donna's roadmap. she doesn't need a desktop — every action she'd take has a real api behind it (gmail, calendar, plaid). computer use earns its keep when you have to drive a system that has no api: legacy enterprise apps, brittle web ui, things you'd otherwise scrape.

15 · the memory tool

the anthropic memory tool is a protocol, not a store. claude makes filesystem-shaped tool calls — view, create, str_replace, insert, delete, rename on a /memories directory — and your handler is what actually reads and writes the bytes. anthropic ships the contract; you ship the persistence.

shape

tools: [
  { type: "memory_20250818", name: "memory" }
]

that's it for the tool decl. the operations claude can call:

commandinputyour handler returns
view{ path, view_range? }directory listing or file contents with line numbers (specific format the prompt expects).
create{ path, file_text }persist the file. error if it exists.
str_replace{ path, old_str, new_str }find/replace exactly once. error on no-match or multi-match.
insert{ path, insert_line, insert_text }splice text after the given line.
delete{ path }remove file or directory recursively.
rename{ old_path, new_path }move within /memories.

auto-included prompt

enabling the tool causes anthropic to prepend this to the system prompt automatically (you don't write it):

// auto-prepended:
IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE.
MEMORY PROTOCOL:
1. Use the `view` command of your `memory` tool to check for earlier progress.
2. ... (work on the task) ...
   - As you make progress, record status / progress / thoughts etc in your memory.
ASSUME INTERRUPTION: Your context window might be reset at any moment ...

so on every turn where memory is in the tool list, the first tool_use you'll see is almost always memory.view("/memories"). budget the iteration count accordingly.

the rules you have to obey

  • restrict all paths to /memories. validate every input against directory-traversal (../, url-encoded %2e%2e, canonicalised symlinks). claude is not the threat model — bad user input riding in via tool args is.
  • return error strings in the exact shape the protocol expects ("Error: The path {path} does not exist", etc.) so claude can interpret failures and recover.
  • cap response size: a huge file return blows the context window. paginate via view_range when files get long.
  • pairs natively with context_management (next section) and server-side compaction — use exclude_tools: ["memory"] so compaction never elides memory writes.

donna's stance

we own the memory layer. the anthropic memory tool is the cleanest interface to it — claude already knows how to use this protocol, the sdk ships BetaAbstractMemoryTool / betaMemoryTool helpers to swap in our backend, and the auto-prompt does the "check memory first" work for free. what sits behind it is ours: pgvector for episodic facts, a structured living profile, a thread log. see [[feedback_donna_memory_own_layer]] — no mem0, no supermemory, we build it.

16 · context management

the request-level context_management field lets anthropic prune the conversation on the server side as it grows, without you having to roll a compaction loop yourself.

context_management: {
  edits: [{
    type: "clear_tool_uses_20250919",
    trigger: { type: "input_tokens", value: 50000 },
    keep:    { type: "tool_uses", value: 5 },     // keep the last 5 tool exchanges
    clear_at_least: { type: "input_tokens", value: 10000 },
    exclude_tools: ["memory"]                       // never prune memory writes
  }]
}

what it actually does: when the request crosses the trigger threshold, anthropic replaces old tool_use / tool_result pairs with stub placeholders that say "n results elided" — keeping the most recent ones intact. the model still sees the conversational arc; it just doesn't see the bytes of an inbox dump from 40 turns ago.

for donna: enable this the moment we start hooking up real integrations. gmail and calendar dumps inflate tool_results fast; without compaction every turn pays for the whole history.

17 · batches

same request shape, fire-and-forget, ~50% off list, up to 24h sla:

const batch = await client.messages.batches.create({
  requests: [
    {
      custom_id: "reflect-2026-05-22-user-001",
      params: {
        model: "claude-opus-4-7",
        max_tokens: 4096,
        system: REFLECTION_PROMPT,
        messages: [...]
      }
    },
    // up to 100k requests per batch
  ]
});

// later:
const status = await client.messages.batches.retrieve(batch.id);
if (status.processing_status === "ended") {
  const results = client.messages.batches.results(batch.id);  // jsonl stream
  for await (const r of results) { ... }
}

donna's batch shape

  • overnight reflection. at 3am, one batch with one request per user — opus reads the day's events, writes tomorrow's surface.
  • retro indexing. when a new integration goes live for an existing user, batch-process the historical backfill instead of streaming.
  • evals. a single batch can run a thousand prompt variations against held-out conversations.

not for: anything interactive. anything where the user is waiting.

18 · token counting

before sending a fat request, ask how fat it is:

const count = await client.messages.countTokens({
  model:    "claude-sonnet-4-6",
  system:   SYSTEM_PROMPT,
  tools:    sdk_tools,
  messages: convo
});

console.log(count.input_tokens);  // e.g. 4231

same accuracy as the real call, no completion cost. use it to:

  • decide whether to compact before sending (the brain could check before every create if we wanted)
  • cost-attribute proactive runs in the ledger before they hit the wire
  • gate context windows — refuse to send a 1m-context request unless the cheaper sonnet path was tried first

19 · errors & retries

the sdk throws typed errors. the ones donna will see:

errorcausestrategy
400 invalid_request_errormalformed payload — usually a broken tool_use/tool_result pair, or a non-alternating messages array.do not retry. fix the request. log the payload.
401 authentication_errorbad api key.do not retry.
403 permission_errorworkspace doesn't have access to a model / beta.do not retry.
404 not_found_errormodel id wrong, or file_id stale.do not retry.
413 request_too_largeover 32mb upload, or context overflow.compact / split. do not retry.
429 rate_limit_errorover your tpm/rpm.retry with exponential backoff. sdk does this by default up to 2 retries; configurable.
500 api_erroranthropic-side bug.retry with backoff.
529 overloaded_erroranthropic capacity event.retry with backoff, longer initial delay (5-10s).

sdk retry config

const client = new Anthropic({
  maxRetries: 3,                // default 2
  timeout:    10 * 60 * 1000,    // 10 min — long thinking budgets need long timeouts
});

donna today runs sdk defaults. the moment we have proactive runs from cron, we'll want explicit retry policies — proactive failures should fall to a backoff queue, not consume the user's turn budget.

20 · observability

two layers, both live in donna today.

langsmith

wrapAnthropic(client) from langsmith/wrappers/anthropic adds a span per messages.create. it's a no-op when LANGSMITH_TRACING is unset. when set, every request — payload, response, usage, latency — is traceable in the langsmith ui.

around it, traceable from langsmith/traceable wraps runTurn as the parent span and each tool handler as a child span. the trace tree mirrors the call tree.

const client = wrapAnthropic(new Anthropic());
export const runTurn = traceable(_runTurn, { name: "donna.runTurn", run_type: "chain" });

// per turn, stamp identity onto the parent trace metadata:
tree.extra.metadata = { run_id, user_id, thread_id };

the ledger

src/donna/ledger.ts is donna's own structured log: one row per modelCallStart, modelCallEnd, toolCalls, finish, all keyed by runId. the ledger and the langsmith trace are cross-referenceable by that id. when something goes wrong you can grep the ledger by runId and replay the exact payload sent to anthropic.
